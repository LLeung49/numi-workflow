# 工作流能力评审（Workflow Capability Review）

-   版本：v0.7-draft
-   状态：设计评审中
-   目标：明确 `numi-workflow` 的能力边界、复用策略和后续演进方向

------------------------------------------------------------------------

# 1. 文档目的

`workflow-capability-review.md` 用于回答：

1.  numi-workflow 为什么存在？
2.  哪些能力应该由 numi 自己负责？
3.  哪些能力应该复用成熟 Agent 编程工作流？
4.  哪些能力需要随着 Agent 能力提升持续演进？

核心原则：

> numi-workflow 不应该重新实现已有成熟工程能力，而应该解决长期 Agent
> 协作中新出现的问题。

numi 的目标不是成为最大的 Skill 集合，而是成为：

> 面向长期软件项目的 Agent 协作治理工作流。

------------------------------------------------------------------------

# 2. 参考对象

本次能力评审主要参考：

-   Superpowers 工作流
-   Matt Pocock Skills
-   Codex / Claude Code 等 Agent 编程实践

其中：

-   Superpowers 强项：
    -   严谨的软件工程执行流程；
    -   设计、计划、开发、测试、评审闭环；
    -   强约束的工程实践。
-   Matt Skills 强项：
    -   灵活的 Agent 工作流组合；
    -   Spec 驱动开发；
    -   项目上下文管理；
    -   用户与 Agent 沟通效率提升。

numi 不替代这些能力，而是在其之上增加长期项目治理能力。

------------------------------------------------------------------------

# 3. numi-workflow 的定位

## 3.1 不是什么

numi 不是：

-   编程框架；
-   测试框架；
-   Git 工作流替代品；
-   代码生成工具；
-   单次任务 Prompt 集合。

------------------------------------------------------------------------

## 3.2 是什么

numi 是：

> 管理人和 Agent 长期协作的软件开发工作流。

核心关注：

-   项目长期依据如何维护；
-   Agent 应该相信什么；
-   什么情况下需要人工决策；
-   如何避免 Agent 自主执行方向漂移；
-   如何证明交付结果可信。

------------------------------------------------------------------------

# 4. 核心理念

## 4.1 项目基线优先

Authority 不翻译为"权威信息"。

按照 numi 术语规范：

> Authority / Authority Pack = 项目基线 / 长期项目依据

项目基线包含：

-   项目目标；
-   需求；
-   架构；
-   工程规范；
-   领域术语；
-   重要决定。

它解决的问题：

> 新 Agent 如何快速理解一个长期项目，并避免重复探索已经确定的问题。

------------------------------------------------------------------------

## 4.2 人负责目标，Agent 负责执行

未来高质量 Agent 开发不是：

    用户：
    一步一步告诉 Agent 怎么做

    Agent：
    机械执行

而应该是：

    用户：
    定义目标、边界、验收标准

            ↓

    Agent：
    理解目标
    规划路径
    执行任务
    收集证据
    发现问题主动升级

            ↓

    用户：
    处理真正需要判断的决策

numi 的价值在于提升这种协作模式。

------------------------------------------------------------------------

## 4.3 面向目标的长期循环

numi 不应该设计成固定流程脚本。

未来应该根据：

-   Agent 能力；
-   项目阶段；
-   用户能力；
-   风险等级；

动态调整。

例如：

新项目：

    更多澄清
    更多设计评审
    更多人工确认

成熟项目：

    更多自主执行
    更少重复确认
    更多自动验收

高风险领域：

    更严格 Gate
    更多证据要求

------------------------------------------------------------------------

# 5. 能力归属模型

## 5.1 Own：numi 自主拥有

这些是 numi 的核心差异化能力。

## 项目基线管理

负责：

-   项目长期依据；
-   版本引用；
-   下游影响判断。

------------------------------------------------------------------------

## 决策生命周期管理

负责：

-   未决事项分类；
-   事实闭环；
-   决策归纳；
-   Gate 状态。

------------------------------------------------------------------------

## Agent 自主边界控制

负责：

-   什么可以自动决定；
-   什么必须升级；
-   什么变化需要重新评审。

------------------------------------------------------------------------

## 证据驱动交付

负责：

-   交付是否完成；
-   依据什么证明；
-   哪些结论可信。

------------------------------------------------------------------------

# 6. Adapt：吸收成熟能力

这些能力已有成熟实践，但需要适配 numi。

## Spec 驱动开发

来源：

-   Matt Skills
-   Superpowers

numi 增强：

-   与项目基线关联；
-   记录依据；
-   管理生命周期。

------------------------------------------------------------------------

## 任务拆解

来源：

-   Superpowers writing-plans
-   Matt to-tickets

numi 增强：

-   任务依赖；
-   新会话接手检查；
-   证据要求。

------------------------------------------------------------------------

## Agent 执行

来源：

-   implement-spec
-   Superpowers executing-plans

numi 原则：

> 不重复实现执行能力，通过接口调用成熟执行 Skill。

------------------------------------------------------------------------

# 7. Reuse：直接复用

以下能力优先复用：

  能力           来源
  -------------- --------------------
  TDD            Superpowers
  Git worktree   Superpowers
  Debug 流程     Superpowers
  Code Review    Superpowers / Matt
  代码实现       Agent 原生能力

原因：

这些主要解决：

> 如何完成工程动作。

而不是：

> 如何长期管理人与 Agent 的协作关系。

------------------------------------------------------------------------

# 8. numi 工作流分层

    用户目标
        |
        v
    项目基线 / 长期项目依据
        |
        v
    功能定义
        |
        v
    任务拆解
        |
        v
    功能交付
        |
        v
    功能验收
        |
        v
    项目演进

对应：

  层级       责任
  ---------- ----------------
  项目基线   长期约束
  功能定义   明确做什么
  任务拆解   明确如何交付
  功能交付   产生代码和证据
  功能验收   判断是否完成
  项目演进   优化未来能力

------------------------------------------------------------------------

# 9. 后续演进方向

## 9.1 能力矩阵

建立：

    能力
     ↓
    是否已有成熟实现
     ↓
    numi 是否需要拥有
     ↓
    复用方式

------------------------------------------------------------------------

## 9.2 外部 Skill 集成

未来：

    feature-deliver

            ↓

    Delivery Backend

            ↓

    implement-spec
    Superpowers execution
    Codex 原生能力
    其它 Agent Runtime

numi 管理能力契约，不绑定具体实现。

------------------------------------------------------------------------

## 9.3 Adaptive Autonomy

长期目标：

让工作流根据：

-   项目成熟度；
-   风险等级；
-   Agent 能力；
-   用户经验；

自动调整自主程度。

------------------------------------------------------------------------

# 10. 设计原则总结

numi-workflow 的核心不是：

> 创建更多 Skill。

而是：

> 用最少的治理能力，让人和越来越强的 Agent 更可靠地完成长期软件项目。

未来随着 Agent 能力增强：

-   执行能力应该越来越外部化；
-   项目基线越来越重要；
-   决策边界越来越清晰；
-   人应该从操作 Agent 转向管理目标和判断。
