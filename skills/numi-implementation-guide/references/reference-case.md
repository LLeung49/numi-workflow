## 一、 实施总览与协作模式

### 1.1 协作工具与开发模式选型
本项目核心开发采用 **Spec-Kit 主体开发 + 手动增量模式**：
- **主体开发阶段**：使用 Spec-Kit，将技术方案与需求拆解为 5 个核心实施阶段（Phase-1 到 Phase-5），由 AI Agent 按规格严格推进；
- **增量演进阶段**：主体功能跑通后，扩展特定投递插件、修 Bug 与性能微调切换为手动提示词模式；
- **工具匹配原则**：Spec-Kit 负责大颗粒度系统骨架与核心能力的规格闭环，手动提示词负责小颗粒度边缘扩展。

### 1.2 与上游基准文档的映射关系
本实施指引不重写需求和架构，而是将其转化为 AI 可消费的工程执行链路：

| 实施阶段输入 | 来源文档与章节 | 承接作用与转化机制 |
| :--- | :--- | :--- |
| **规格定义 (Specify)** | 《需求规格说明书》(DemandAnalysis.md) | 提取业务规则、5 个核心交付阶段与验收场景 |
| **方案计划 (Plan)** | 《技术方案》(TechnicalSolution.md) | 映射为系统分层、Maven 模块划分、核心接口与存储模型 |
| **Harness 约束** | 需求设计目标 + 方案技术决策 | 提炼为不可退让的架构硬禁令与只读受保护路径 |
| **阶段验收标准** | 需求验收场景 + 方案系统不变量 | 转化为各阶段的验收 Demo 与自动化回归用例 |

### 1.3 接手者的最短阅读路径 (2 分钟原则)
为确保无会话记忆的开发者或 AI 能够在 2 分钟内精准开工，严格遵循以下顺序阅读：
1. **读指引（本文档）**：明确系统推进路线图、受保护路径与 Harness 约束；

4. **读断点（`docs/session-handoff.md`）**：确认当前最新提交、所在分支与下一步具体任务。

## 二、 三层输入体系与公共底座

### 2.1 项目级基准文档
开工前固定四份基础文档：调研（IndustryResearch.md）、需求（DemandAnalysis.md）、方案（TechnicalSolution.md）与本文档。
> ⚠️ **冲突仲裁原则**：需求或架构冲突时，必须先人工确认修改基准文档，严禁不同 Agent 自行猜测裁决。

### 2.2 公共契约底座 (Common Base)
所有模块共享且不可重复发明的核心资产：
- **公共领域实体与状态**：`Message`、`MessageStatus`、`SinkType`、`SinkConfig` 强类型模型；
- **核心 SPI 抽象接口**：`StoragePlugin`、`TimeWheel`、`Sink`、`Router` 等核心顶层抽象；
- **模块协作门面**：`TimeWheelRegistry`、`ClusterView`、`DueMessageHandler` 等连接接口；
- **统一通信协议与存储语义**：HTTP/gRPC 字段语义、Redis 与 ETCD Key 空间规范；
- **全局安全与日志红线**：禁止在日志中打印 payload 和明文密钥。

> **先闭环原则**：公共底座应先实现并完成 Review 锁定。后续业务模块只引用底座契约，严禁复制接口或私自改动方法签名。

### 3.2 阶段细化拆解

#### Phase-1：公共契约底座与工程骨架
- **核心目标**：建立多模块 Maven 骨架，冻结共享实体模型与 SPI 抽象，建立根级构建与 CI 验证。
- **涉及模块**：`when-common`、`when-sink-spi`、根 `pom.xml`。
- **Task 拆分思路**：
  - `Task 1.1`：初始化多模块 Maven 骨架与依赖版本锁定（Spotless/Checkstyle 配置）；
  - `Task 1.2`：定义 `Message`、`MessageStatus` 枚举与公共错误码；
  - `Task 1.3`：定义 `StoragePlugin`、`TimeWheel`、`Sink` 等核心 SPI 抽象接口。
- **关键技术陷阱**：SPI 接口中严禁出现具体中间件（如 Jedis、KafkaProducer）特有类，只允许 JDK 原生与 Common 抽象类型。
- **阶段验收 Demo**：
  - `mvn clean test` 编译打包全绿，契约模型序列化与反序列化测试全通过。

#### Phase-2：单机核心调度与存储闭环
- **核心目标**：实现 Redis 存储插件与多层时间轮，打通单机消息提交、持久化、调度入轮与到期触发闭环。
- **涉及模块**：`when-storage-redis`、`when-timewheel`、`when-delivery`、`when-app`（单机启动入口）。
- **Task 拆分思路**：
  - `Task 2.1`：基于 Redis Hash 与 ZSet 实现原子消息写入与索引持久化；
  - `Task 2.2`：实现内存分层时间轮（HashedWheelTimer），支持动态槽位推进与时间步长调整；
  - `Task 2.3`：实现单机消息到期分发器（DueMessageHandler），将到期消息投递给桩 Sink；
  - `Task 2.4`：在 `when-app` 中组装 Composition Root，完成生命周期联动。
- **关键技术陷阱**：
  - 调度线程严禁执行同步阻塞 IO（网络调用必须异步移交给工作线程池）；
  - 时钟（Clock）必须抽象为可注入接口，严禁写死 `System.currentTimeMillis()`。
- **阶段验收 Demo (Demo 一)**：
  - **场景**：向单机实例提交 1 条 3 秒后延时消息；
  - **运行**：运行单机冒烟测试用例 `mvn test -pl when-app -Dtest=SingleNodeSmokeTest`；
  - **预期**：3 秒后桩 Sink 捕获到该消息，控制台打印触发日志，状态流转为 DELIVERED。

#### Phase-3：多协议投递插件体系
- **核心目标**：实现工业级 HTTP 与 Kafka 投递插件，具备连接池复用、超时保护与有界重试能力。
- **涉及模块**：`when-sink-http`、`when-sink-kafka`。
- **Task 拆分思路**：
  - `Task 3.1`：实现 HTTP Sink，配置池化连接管理器与 Connection/Socket Timeout；
  - `Task 3.2`：实现 Kafka Sink，配置 Batch 大小与 Producer 确认级别；
  - `Task 3.3`：实现基于退避算法的重试机制，确保异常场景不发生消息雪崩。
- **关键技术陷阱**：HTTP/Kafka 客户端必须在组件初始化时池化创建，严禁每次投递时重复 new 客户端导致连接泄漏。
- **阶段验收 Demo (Demo 二)**：
  - 运行 MockWebServer 测试套件，验证 200 成功投递与 500 触发有界重试行为。

#### Phase-4：集群协调与高可用 HA
- **核心目标**：基于 ETCD 实现多节点注册、心跳保活、Master 选举与时间轮槽位动态 Rebalance。
- **涉及模块**：`when-cluster`、`when-timewheel`。
- **Task 拆分思路**：
  - `Task 4.1`：实现 ETCD 节点注册、租约续约与成员 Watcher；
  - `Task 4.2`：实现 Controller 选举与基于 Raft 租约的选主机制；
  - `Task 4.3`：实现时间轮槽位在存活节点之间的哈希环分配与故障重新分配。
- **关键技术陷阱**：Master/Slave 必须分配在不同物理节点；Controller 故障转移必须具备递增 Epoch Fencing，杜绝脑裂脏写。
- **阶段验收 Demo (Demo 三)**：
  - 启动 3 节点模拟集群，杀死当前 Master 节点，观察 ETCD Watch 触发选举并在 2 秒内产生新 Master，其余节点平滑接管。

#### Phase-5：服务化暴露与整体验收
- **核心目标**：暴露 HTTP/gRPC 对外提交接口，提供 Web 管理台，完成最终 HA 故障演练与验收。
- **涉及模块**：`when-api`、`when-admin-api`、`when-e2e-test`。
- **阶段验收 Demo (Demo 四)**：
  - 运行端到端验收脚本，验证全系统在断网、重启等异常干扰下的投递可靠性，满足 PRD 第 10 章所有指标。

### 3.3 并行实施与防冲突准则
- **允许并行开发**：Phase-1 冻结后，Phase-3（HTTP/Kafka 插件）与 Phase-4（集群协调）文件完全解耦，可由不同 Agent 并行推进；

## 四、 项目级 Harness 规则与质量门禁

### 4.1 核心不可退让原则 (架构硬性禁令)
1. **调度主循环零阻塞**：时间轮轮转线程绝对禁止执行任何同步网络请求或磁盘刷盘；
2. **连接池资源有界**：HTTP 连接池与线程池必须显式配置上限，杜绝无界线程堆积；
3. **禁止大 Key**：Redis 禁止使用无分片的全局大 ZSet 或大 Hash；
4. **敏感载荷脱敏**：日志、指标与 Admin API 严禁打印 payload 明文及节点密钥；
5. **绝对防作弊底线**：**严禁通过删除测试用例、放宽断言公差、注释门禁或加 `@skip` 伪造测试绿灯！**

### 4.2 受保护路径清单 (Protected Paths)
以下路径对负责功能实现的 Agent 设定为**只读受保护**，严禁擅自修改：
```text
when-common/src/main/java/org/when/common/contracts/    # 公共领域模型与 SPI 抽象
when-acceptance/src/test/                               # 系统级宪法不变量与验收测试
.github/workflows/                                      # CI 门禁配置文件
```

### 4.3 务实的质量门禁 (Quality Gates)
根据项目技术栈，代码合并前需在本地终端通过以下门禁：

| 门禁层次 | 门禁目标 | 审查对象与标准 | 本地执行命令 | 失败处理动作 |
| :--- | :--- | :--- | :--- | :--- |
| **G1 规范与 Lint** | 统一编码风格与静态扫描 | Spotless 格式校验与 Checkstyle | `mvn spotless:check checkstyle:check` | 修复代码，不放宽规则 |
| **G2 契约兼容** | SPI 抽象向后兼容 | 接口签名与抽象一致 | `mvn test -pl when-common` | 保持契约稳定，严禁私改接口 |
| **G3 系统不变量** | 架构硬性底线回归 | 时间轮非阻塞、Redis 原子操作 | `mvn test -Dtest=*InvariantTest` | 触碰底线，立即阻断停机 |
| **G4 单元与组件** | 业务逻辑测试覆盖 | 主路径与异常分支测试通过 | `mvn test` | 修复实现 Bug，严禁删测试 |
| **G5 阶段验收** | 阶段目标功能验收 | 跑通当前阶段对应的验收 Demo | `mvn verify -Pacceptance` | 真实命令执行，不造假证据 |

> 📌 **长效规范说明**：质量门禁定义命令体系与标准，**本文档不记录单次运行的临时结果（如通过条数），测试执行快照记录于 `STATUS.md` 或会话交接单中**。

## 五、 四维 Review 审查清单 (Review Checklist)

合并分支前，Reviewer 依据四维清单严格核验：

### 5.1 正确性
- 持久化成功之前是否可能提前返回成功或入内存调度；
- 到期触发是否错误删除了仍需重试/排查的消息事实；
- 状态转换是否具备原子 CAS 语义；
- 主备副本是否可能落在同一物理节点；
- 至少一次投递语义与基于唯一 ID 的幂等是否贯穿始终。

### 5.2 并发与资源
- 调度主循环线程是否包含阻塞性同步网络或磁盘 IO；
- 客户端连接池是否复用，连接池与线程池是否有界；
- 服务优雅下线是否先摘流量、再交接、最后释放资源。

### 5.3 安全与防作弊
- 日志、指标或管理 API 是否打印明文载荷与私钥；
- 代码与部署配置中是否存在硬编码凭据；
- 测试用例是否被擅自删除、放宽断言或添加 `@skip`。

### 5.4 可验证性
- 时钟、网络故障、存储异常是否可注入测试；
- 测试断言是否验证真实系统行为而非实现细节；
- 交付物是否可在干净环境中完整复现走通。

## 七、 活文档治理、失败停机与断点交接

### 7.1 活文档 vs 死文档极简维护
- **死文档（时点基线归档）**：调研（IndustryResearch.md）、需求（DemandAnalysis.md）写完归档，不频繁改动；
- **活文档（与代码共生）**：公共契约、实施指引与门禁配置。**必须纳入 PR 代码审查闭环**（改接口必须在同一个 PR 里同步更新活文档）。

### 7.2 失败停机规则
- **普通实现 Bug**：允许在局部分支内修复重试，上限 **3 次**；
- **规格冲突 / 需改受保护基线**：**立即停机 (STOP)，0 次重试**，提交决策单；
- **不变量破裂（如数据污染）**：**立即停机 (STOP)，0 次重试**，保护现场；
- **连续 2 次无进展（Zero-diff 熔断）**：强制停止循环，将现场保存至交接单。

### 7.3 跨会话断点交接规范 (`docs/session-handoff.md`)
在开工交接、切片交付或停机中断时，向 `docs/session-handoff.md` 追加记录：

```markdown

- **交付切片与分支**：[切片编号，如 SLICE-01] | `[分支名称]`
- **Git 提交基线**：`[Commit SHA 或初始基线]`
```
