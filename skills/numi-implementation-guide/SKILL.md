# AI 编程实施指引编写技能 (Implementation Guide)

这份文档是连接“上游需求/架构设计”与“代码工程落地”的总纲领与路线图。

它的核心使命是：**回答怎么落地做出来。它对标 Oryxos 与 When 的工程精髓，既规划系统分阶段实施的宏观路线图（User Stories / Phases），又为 AI 编码设立严格的工程边界与 Harness 验收机制。**

采用项目语言与位置，新项目默认输出 `docs/AiProgrammingGuide.md`。

---

## 一、 核心定位与设计哲学（从 Oryxos 与 When 提炼）

一份高质量的《AI 编程实施指引》必须兼具**“战略实施路线图”**与**“工程防护 Harness”**：

1. **战略路线图（Implementation Roadmap，骨架）**：
   - 绝不能通篇只有静态门禁检查命令，而没有业务系统的实施节奏；
   - 必须将上游需求与技术方案，拆解为依赖清晰的实施阶段（如 Oryxos 的 US-1~US-5，或 When 的 Phase A/B/C）；
   - 明确每个阶段的**核心目标、涉及模块/目录、Task 拆解颗粒度、关键技术陷阱与阶段验收 Demo**。
2. **工程级 Harness（边界与底线）**：
   - Harness 是让 AI 做好事情所需的上下文、边界、约束和验收体系；
   - 包含**核心宪法原则**（如 Oryxos 8 条铁律、When 架构硬禁令）与**受保护只读路径**（契约、不变量、验收测试严禁擅改）；
   - 严禁通过“删除测试、放宽断言、注释门禁”伪造通过。
3. **务实的质量门禁（质量阶梯）**：
   - 适配项目真实技术栈（如代码规范、类型检查、契约兼容、不变量回归、单元测试、端到端冒烟）；
   - 门禁必须真实可跑，严禁凭空臆造。未配置的检查项应明确指出搭建路径，而非形式主义填空。
4. **分支与工作区物理隔离纪律（Branch & Worktree Isolation）**：
   - **串行单卡单分支**：主干分支（`main` / `master`）零业务直改；每张原料卡必须从最新主干切出 `feat/<slice-id>-<slug>` 独立分支，验收后 `--no-ff` 留痕合并，严禁套娃分支或多卡混写；
   - **并行一卡一 Worktree**：满足公共底座已合入、修改文件零重叠、测试环境无争抢三前提时方可并行，且必须通过 `git worktree` 为每张并行卡挂载独立物理目录，按依赖拓扑序依次回归合入。
5. **长效指南与运行时状态严格分离（Clean Separation）**：
   - **实施指引是长效活文档**，指导整个开发周期的工作流；
   - **严禁将时点运行事实写入本文档**：如当前的 Git commit hash、具体的单测执行结果（如“76 passed, 1 skipped”）、临时环境变量配置等，这些必须记录在 `STATUS.md`、`session-handoff.md` 或 CI 报告中。
6. **清晰的失败自愈预算与跨会话交接（session-handoff）**：
   - 普通实现 Bug 最多自愈 3 次；连续 2 次无进展（Zero-diff）或不变量破裂立即停机；
   - 停机或会话结束时，将断点保存至 `docs/session-handoff.md`。

## 二、 工作执行流程

### 阶段一：前置资产读取（硬性门禁）
动笔前必须调用 `read_file` 完整读取以下文件：
1. `references/writing-guide.md` —— 掌握实施拆解方法、Harness 架构、受保护路径与就绪度反问法则；
2. `references/reference-case.md` —— **研读标杆案例，掌握兼具“实施阶段拆解 (Roadmap)”与“Harness 门禁”的工业级文档结构**；
3. `assets/document-template.md` —— 获取标准实施指引骨架。

### 阶段二：开工就绪度反问与人机共创（Readiness & Co-Creation Gate）
高质量实施指引是人类与 AI 的协作契约。动笔前必须核验以下 **5 项前提条件**：
1. **实施模式与协作工具确定**：本项目主体开发采用什么协作范式？（如基于 Spec-Kit 驱动、Loop Engineering 运行器、还是手动提示词切片交付？）
2. **实施阶段拆解（User Stories / Phases）对齐**：系统核心功能按什么阶段与顺序推进？每个阶段的验收 Demo 是什么？
3. **真实环境与构建工具链核验**：项目使用的包管理器、依赖锁定与测试命令是什么？（实机核查/向人类确认，严禁脑补虚假命令）
4. **受保护路径与防作弊红线划定**：哪些核心契约、不变量测试与基准用例对业务 Agent 设为只读？
5. **失败停机与交接规则对齐**：重试预算上限是多少（≤3次）？发生何种冲突必须立即停机？

> 💡 **若输入不足**：必须在对话中输出《开工就绪度诊断 (Implementation Guide Readiness)》，检查已有配置，若无法断定，主动向人类确认实施分期与真实运行命令。

### 阶段三：起草实施指引文档
1. 按照 `document-template.md` 填充正文；
2. 重点写透 **实施阶段拆解与实施路线图 (Implementation Roadmap)**，将方案转化为可被分步执行的阶段；
3. 明确受保护路径清单与实测可跑的质量门禁；
4. 输出至 `docs/AiProgrammingGuide.md`。

## 三、 交付检查清单

- [ ] **资产读取门禁**：动笔前是否已实际读取指南、**标杆案例 (`reference-case.md`)** 与模板？
- [ ] **实施路线图完整**：是否包含清晰的阶段拆解（US-1~US-n 或 Phase A/B/C）、涉及模块、任务颗粒度与阶段验收 Demo？
- [ ] **分支与并行隔离明确**：是否规定了一卡一分支 `--no-ff` 归并闭环，以及并行开发的三前提与 `git worktree` 物理隔离协议？
- [ ] **最短阅读路径**：接手者能否在 2 分钟内看懂当前该读什么、从哪个阶段切入？
- [ ] **受保护路径明确**：是否锁定了禁止随意篡改的公共契约与核心测试断言？
- [ ] **质量门禁真实可跑**：列出的检查命令是否符合项目实际技术栈？
- [ ] **长效文档干净**：是否杜绝了写入具体 commit、测试通过条数等易腐化的运行时状态？
- [ ] **失败停机与交接**：是否明确规定了 Bug 修复上限（≤3次）以及断点落盘机制？
