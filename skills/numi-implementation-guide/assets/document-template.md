### 3.3 分支隔离与串/并行协作规范 (Branch & Worktree Isolation)

#### 1. 串行开发：单卡单分支与 `--no-ff` 归并闭环
- **严禁主干直写与多卡混写**：主干分支（`main` / `master`）仅用于承载已验收基线与合并节点；每一个原子需求切片必须对应一个独立分支 `feat/<slice-id>-<slug>`（直接绑定原料卡编号，防止抢号）。
- **标准串行流转**：
  1. 开工前核验上一切片已合入主干且工作区干净：`git switch main && git status --short`；
  2. 基于最新主干创建本切片分支：`git switch -c feat/<slice-id>-<slug> main`（严禁从上一个未合并或已合并的 `feat/*` 分支直接切新分支）；
  3. 分支内完成 SpecKit 全流程与 6 证据 DoD 验收报告，等待人类 Review；
  4. 人类验收提交后以 `--no-ff` 留痕合入主干：`git switch main && git merge --no-ff feat/<slice-id>-<slug>`，随后再从更新后的 `main` 开启下一切片。

#### 2. 并行开发：三前提准入与 `git worktree` 物理目录隔离
- **并行准入三前提（任一不满足则严禁并行，退回串行）**：
  1. **公共底座已锁定**：前置共享模型、SPI 契约与基础表结构已合入 `main`；
  2. **修改路径零重叠**：各并行切片原料卡第 11 节交付物文件集合 100% 互不相交（共享入口组装留给后续串联切片）；
  3. **测试资源无争用**：各自验收测试使用独立临时库/随机端口，互不干扰。
- **强制 Worktree 隔离（严禁多 Agent 共用同一工作目录）**：
  - 确保 `.worktrees/` 已加入 `.gitignore`；
  - 从 `main` 为每张并行原料卡挂载独立工作区：`git worktree add .worktrees/<slice-id> -b feat/<slice-id>-<slug> main`，各 Agent 严格在各自 Worktree 目录内独立运行（互不覆盖代码与 `.specify/feature.json`）。
- **按依赖图顺序归并（二次回归门禁）**：
  - 合并顺序严格遵循路线图 DAG 顺序，不按谁先完成决定；
  - 第一个并行切片验收后 `--no-ff` 合入 `main` 并在 `main` 上跑绿回归测试；后续并行切片在合入前，**必须先在自身 Worktree 内执行 `git merge --no-edit main` 同步最新主干并重跑全量回归测试全绿**，确认无跨切片冲突后再合入 `main` 并在 `main` 验证全绿。

#### 3. Worktree 与历史分支零数据丢失清理协议 (Zero-Data-Loss Cleanup)
- **AI 权限红线**：AI Agent 严禁自动执行任何删除分支（`git branch -d/-D`）或移除目录（`git worktree remove`）命令，仅允许输出只读体检清单供人类核对执行。
- **Worktree 安全拆除前置三检**（⚠️ 警惕：`git worktree remove` 即使不加 `--force` 也会静默永久删除 `.gitignore` 忽略的 `.env`、`*.db` 等本地文件！）：
  1. 合入后的 `main` 已重跑门禁测试全绿；
  2. `git -C .worktrees/<slice-id> status --porcelain` 输出严格为空（无漏提文件）；
  3. `git -C .worktrees/<slice-id> status --ignored --short` 确认除纯工具缓存外无孤本 `.env*`、`*.db`、`*.sqlite` 或数据文件；
  4. 三检通过后回到主仓执行：`MAIN_ROOT=$(git worktree list --porcelain | awk '/^worktree /{print substr($0,10); exit}') && cd "$MAIN_ROOT" && git worktree remove .worktrees/<slice-id> && git worktree prune --verbose`。
- **阶段收官分支清理（延时一拍 + 真合并第二父节点核验，防误杀 0 提交新分支）**：
  - 单卡合入后暂留分支指针作回滚缓冲，待阶段（Phase）联调稳定后先运行只读预览（仅匹配未挂载 Worktree 且确系 `main` 上 Merge Commit 第二父节点的 `feat/*` 分支）：
    ```bash
    MERGED_PARENTS=$(git log main --merges --format='%P' | awk '{print $2}')
    git for-each-ref --format='%(refname:short)|%(objectname)|%(worktreepath)' refs/heads/feat/ | while IFS='|' read -r br sha wt; do
      [ -z "$wt" ] && printf '%s\n' "$MERGED_PARENTS" | grep -qx "$sha" && echo "[安全可删] git branch -d $br"
    done
    ```
  - 对未合入主干但确认废弃的实验僵尸分支，清理前先打归档标签 `git tag archive/<branch-name> <branch-name>` 永久留底，再手动移除分支引用。

## 四、 项目级 Harness 规则与质量门禁

### 4.1 核心不可退让原则 (宪法原则 / 架构硬性禁令)
以下原则为本项目不可协商的铁律，违背任意一条直接阻断提交：
1. **架构单向依赖**：业务层严禁反向依赖具体插件实现；
2. **状态与数据安全**：核心状态外置持久化，严禁内存状态无备份退出；
3. **敏感凭据脱敏**：日志、指标与管理端点严禁打印明文载荷与密钥；
4. **资源边界可控**：连接池、线程池与队列必须显式配置有界上限；
5. **绝对防作弊底线**：**严禁通过删除测试、放宽断言公差、注释门禁或加 `@skip` 来伪造通过！**

### 4.2 受保护路径清单 (Protected Paths)
以下路径对负责业务实现的开发 Agent 设定为**只读受保护**，严禁擅自修改：
```text
[例如: src/common/contracts/]          # 已冻结的公共契约与接口
[例如: tests/invariants/]              # 系统级宪法不变量测试套件
[例如: tests/acceptance/]              # 端到端场景验收测试基准用例
[例如: .github/workflows/]             # 质量门禁执行脚本与 CI 配置
```

### 4.3 务实的质量门禁 (Quality Gates)
根据本项目实际技术栈，配置以下可运行门禁（按实际支持能力逐步启用）：

| 门禁层次 | 门禁目标 | 审查对象与通过条件 | 本地执行命令 (实机对齐) | 失败处置动作 |
| :--- | :--- | :--- | :--- | :--- |
| **G1 规范与 Lint** | 代码风格与安全扫描 | 统一编码风格，无未引用依赖 | `[如: ruff check . / mvn checkstyle]` | 修复代码，不放宽规则 |
| **G2 静态类型** | 强类型安全性 | 消除隐式 Any，严格类型推断 | `[如: mypy src/ / tsc --noEmit]` | 补齐类型，严禁类型降级 |
| **G3 契约兼容** | 公共接口向后兼容 | 接口签名与公共底座完全一致 | `[如: pytest tests/contracts/]` | 保持契约稳定，严禁私改接口 |
| **G4 系统不变量** | 核心架构不变量回归 | 资源上限、沙箱白名单、状态机守恒 | `[如: pytest tests/invariants/]` | 触碰底线，立即阻断停机 |
| **G5 单元与集成** | 逻辑覆盖与异常分支 | 业务逻辑测试全绿，断言真实行为 | `[如: pytest / mvn test]` | 修复实现 Bug，严禁删改测试 |
| **G6 阶段/端到端** | 阶段 Demo 与场景验收 | 满足对应阶段验收 Demo 场景 | `[如: pytest tests/acceptance/]` | 真实命令执行，不造假证据 |

> 📌 **长效规范说明**：未配置的项目（如初期未接入静态类型检查器）明确标出规划方案，不得随意编造不可运行的命令。**本文档不记录单次运行的临时结果（如通过条数），测试执行快照记录于 `STATUS.md` 或会话交接单中**。

## 五、 四维 Review 审查清单 (Review Checklist)

合并分支前，必须依据四维清单严格核验代码：

| 维度 | 审查要点 | 违规一票否决项 |
| :--- | :--- | :--- |
| **1. 正确性** | 持久化成功前是否提前确认返回；状态转换是否原子/条件校验；一致性、事务或幂等模型是否按设计落实；异常分支是否安全处理。 | 发现并发竞态、状态双处理或数据丢失隐患。 |

## 七、 活文档治理、失败停机与断点交接

### 7.1 活文档 vs 死文档极简维护
- **死文档（时点基线归档）**：调研（IndustryResearch.md）、需求（DemandAnalysis.md）写完归档，不频繁改动；
- **活文档（与代码共生）**：公共契约、实施指引与门禁配置。**必须纳入 PR 代码审查闭环**（改接口必须在同一个 PR 里同步更新活文档）。

### 7.2 失败分类与停机准则
- **普通实现 Bug**：允许在局部分支内修复重试，上限 **3 次**；
- **规格冲突 / 需改受保护基线**：**立即停机 (STOP)，0 次重试**，提交决策单；
- **不变量破裂（如数据污染）**：**立即停机 (STOP)，0 次重试**，保护现场；
- **连续 2 次无进展（Zero-diff 熔断）**：强制停止循环，将现场保存至交接单。

### 7.3 跨会话断点交接规范 (`docs/session-handoff.md`)
