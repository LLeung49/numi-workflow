# 项目技术方案与架构设计技能 (Technical Design)

这份文档对应软件研发流程中的 **Plan（方案设计）** 阶段。

它的核心使命是：**回答怎么做。技术决策、架构分层、模块依赖在此处定死。每个决策要写清为什么这么选、放弃了什么。必须清楚回答四个问题：系统怎么拆、为什么这样选、接口和数据怎么设计、风险是什么。**

采用项目语言与位置，新项目默认输出 `docs/TechnicalSolution.md`。

---

## 一、 写作核心原则（说程序员人话、重权衡与公共契约）

1. **回答 How，严格承接 What**：
   - 技术方案必须完整覆盖需求文档中的功能闭环与验收情境；
   - 严禁借架构之名擅自扩缩业务范围，或增加未经讨论的无用功能。
2. **严禁凭空脑补（消歧提问与显式留白）**：
   - 遇到重大架构选型分歧（如存储选型、通信协议、部署形态），**严禁 AI 擅自拍脑袋做决定**；
   - 必须主动暂停，向用户提出 2~3 个具体的选型权衡问题（对比优缺点并给出推荐），由用户拍板；
   - 暂时无法确定的具体性能阈值或部署配置，显式标注 `[待定 / 待压测标定: xxx]`，在文首《待决事项清单》中汇总统报。
3. **每个决策写清为什么选、放弃了什么**：
   - 拒绝只给结论。每一个核心架构决策，必须说明选型理由，并明确写出“放弃了什么方案、为什么放弃”。
4. **公共底座与公共契约先行（Contract-First）**：
   - **先定义所有模块共用的数据结构、状态和接口，再分别实现各模块**；
   - 跨模块共享的领域模型（Entities）、状态枚举（Enums）与抽象接口（SPI）必须先行统一，下游模块只能单向依赖公共契约。
5. **技术“不做清单”（Anti-Scope）与系统不变量**：
   - 明确技术边界，严禁为了“炫技”引入不需要的重型中间件；
   - 提炼系统绝对不能破坏的底线不变量（Invariants：如数据守恒、状态外置、测试断言不可篡改）。
6. **领域统一语言与分层契约建模 (DDD & Two-Tier Modeling)**：
   - 严禁在技术方案的公共实体与接口中使用 `kind`、`expected_keys` 等偷懒实现黑话，必须确立强类型领域枚举与值对象；
   - 接口建模遵循两级分层：操作者发起的“业务意图命令 (Command)”与服务层内部补齐的“执行上下文 (ExecutionContext)”，杜绝把系统内部状态直接暴露给外部调用方。

## 二、 工作执行流程

### 阶段一：前置资产读取（硬性门禁）
动笔前必须调用 `read_file` 完整读取以下文件：
1. `references/writing-guide.md` —— 掌握架构决策模式、就绪度反问、公共底座契约先行与不变量提炼；
2. `references/reference-case.md` —— **研读标杆案例，学习优秀技术方案在架构决策透明度、模块分层与 SPI 抽象上的严密性**；
3. `assets/document-template.md` —— 获取标准技术方案骨架。

### 阶段二：开工就绪度反问与人机共创（Readiness & Co-Creation Gate）
一份能够让开发人员和下游 Agent 坚定落地、无架构漂移的技术方案，核心在于“为什么选与放弃了什么”的真实决策，绝不能靠 Agent 随意挑选第三方库。

#### 1. 高质量技术方案必备的 5 项前提条件（动笔前必须反问自检）：
- **上游需求基线就绪**：`docs/DemandAnalysis.md` 是否已完成并明确了业务场景与 Anti-Scope？（上游基线）
- **技术栈与运行时环境约束**：项目目标语言版本、操作系统依赖、进程模型（单进程单机/微服务/CLI/Daemon）是什么？（人类提供）
- **关键技术权衡决策（Trade-offs）**：核心组件选型（如存储用 SQLite 还是 PostgreSQL？通信用进程内 SPI 还是 RPC？）的对比理由与放弃代价是什么？（人类裁决）
- **跨模块公共契约先行 (Contract-First)**：所有模块依赖的通用实体、枚举与核心接口是否已初步形成共识？（人类与 Agent 协同）
- **系统级不可动摇的不变量 (Invariants)**：如数据一致性、状态外置、涉外 IO 沙箱、门禁防作弊底线。（人类与 Agent 共同确立）

#### 2. 就绪度诊断与交互规则：
- **若输入不足（需求未清或架构关键选型未定）**：
  - **严禁直接代用户选型并编写几千行假接口！**
  - Agent 必须在对话中先输出《开工就绪度诊断 (Technical Design Readiness)》，指出哪些选型与边界缺失，并针对 2~3 个核心选型（如“存储方案采用方案 A 还是方案 B”）列出优缺点与代价，供人类拍板。
- **若输入基本就绪**：
  - 先就公共契约（Entities & SPI）与系统不变量达成共识，确认后再展开具体模块设计。
- **未决事项显式留白**：
  - 尚未经压测标定的指标（如 QPS、超时阈值），正文显式标注 `[待压测标定: xxx]`，在文首《待决事项清单》汇总，严禁凭空编造假数字。

### 阶段三：起草架构方案文档
1. 按照 `document-template.md` 填充正文；
2. 绘制分层架构图、调用链路，定义核心领域模型与 SPI 接口；
3. 写清不做清单与系统不变量；
4. 未决事项在文首《待决事项清单》中列出，输出至 `docs/TechnicalSolution.md`。

## 三、 交付检查清单

- [ ] **资产读取门禁**：动笔前是否已实际调用 `read_file` 读取指南、**标杆案例 (`reference-case.md`)** 与模板？
- [ ] **消歧与真实性**：选型模糊时是否已向用户提问？未决项是否显式标注？有无擅自引入复杂组件？
- [ ] **决策有理有据**：每个核心决策是否写明了“为什么选”以及“放弃了什么”？
- [ ] **公共契约就位**：是否先行统一定义了跨模块共享的领域模型与接口抽象？
- [ ] **单向依赖保证**：系统各模块之间是否单向依赖，杜绝了循环引用？
- [ ] **不做清单与底线**：是否明确了技术不做清单与不可动摇的系统不变量？
