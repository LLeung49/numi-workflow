# 功能交付

目标：让人和 Agent 在功能执行阶段始终能够回答五个问题：

1. **当前 Feature 到哪里了？**
2. **哪些开发任务已经完成，完成的证据是什么？**
3. **当前哪些工作可以继续，哪些被阻塞？**
4. **是否出现需要人工判断或返回上游重新定义的变化？**
5. **如果更换 Agent / session，下一位执行者最少需要知道什么？**

本 Skill 管理的是 **Feature 交付状态、证据和协作边界**，不是 Agent Runtime，也不是代码实现 Skill。

## 0. 先确认是否应该进入功能交付阶段

读取当前 Feature 的：

- 已批准功能规格；
- Gate B（功能规格评审）记录；
- 已批准开发任务 / 任务依赖；
- Gate C（任务拆解评审）记录；
- 已存在的交付状态记录（如果有）；
- 当前执行结果、测试结果、review 结果和开发中新发现。

开始前确认：

1. 功能定义状态已经批准；
2. 任务拆解准备状态已经通过；
3. 当前开发任务没有隐式改变已批准功能行为；
4. 不存在已知、仍未关闭的上游 blocker。

如果功能目标、范围、公共行为或风险边界仍未确认：

> 停止交付状态推进，返回 `$feature-shape`。

如果功能规格仍然有效，但任务拆解本身需要调整，例如：

- 新发现导致任务依赖关系变化；
- 某张任务已经被其它任务完整覆盖；
- 原任务粒度无法被新会话可靠接手；
- 需要新增 / 合并 / 拆分开发任务；

则：

> 保留现有执行证据，返回 `$feature-slice` 更新任务拆解。

不要在本 Skill 中静默重写功能规格或任务图。

## 1. 建立或更新交付状态记录

默认在当前 Feature 工作目录维护：

```text
delivery.md
```

如果项目已有明确的等价交付状态文件，复用现有位置，不重复创建。

`delivery.md` 是**动态执行事实记录**；已批准的 `spec.md` / `tasks.md` 仍然分别代表功能规格和任务拆解，不因为执行状态变化而被改写成运行日志。

推荐最小结构：

```markdown
# <Feature> 交付状态

功能规格:
任务拆解:
状态:
最后更新:

## 当前摘要
- 当前阶段:
- 当前可继续工作:
- 当前阻塞:
- 需要人工判断:

## 开发任务状态

| 开发任务 | 状态 | 主要证据 | 阻塞 / 备注 |
|---|---|---|---|
| TICKET-01 | 已完成 | ... | ... |

## 执行证据
- ...

## 开发中新发现
- ...

## 需要上游处理
- 无 / ...

## 续接所需最小上下文
- ...
```

不要为了“结构完整”生成额外 YAML / JSON / 数据库状态。

v0.7 的首选是一个人和 Agent 都容易阅读、容易通过 Git 审查的 Markdown 状态记录。

## 2. 状态只描述事实，不驱动执行引擎

开发任务状态优先使用自然中文：

- 未开始；
- 可开始；
- 进行中；
- 待验证；
- 已完成；
- 阻塞；
- 需上游复审。

Feature 层可以使用：

- 可开始；
- 交付中；
- 验证中；
- 阻塞；
- 待验收；
- 已完成。

状态变化必须有事实依据。

例如：

```text
进行中 → 已完成
```

不能只因为 Agent 说“完成了”。

至少需要与该任务验收标准相匹配的执行证据。

本 Skill 可以根据已批准依赖关系**展示当前可继续的工作单元**，但不负责：

- 给不同 Agent 分派任务；
- 决定用哪个模型；
- 自动启动 subagent；
- 管理 worktree；
- 决定具体实现顺序。

执行方式由用户、Coding Agent、Agent Harness 或被复用的成熟 Workflow 决定。

## 3. Evidence over Assertion：完成必须有证据

每个“已完成”主张都必须能回答：

> 为什么认为它已经完成？

证据可以包括：

- 实际运行过的测试命令与结果；
- 代码变更的 commit / diff / 文件与 symbol；
- 可复现的运行结果；
- Code Review 结果；
- 生成的工作产物；
- 验收检查结果。

优先记录稳定引用：

- commit；
- 文件 + symbol；
- 测试名；
- 命令；
- 工作产物路径。

不要只记录易漂移的行号。

推荐写法：

```markdown
- TICKET-03
  - 主张: ETF fallback 已完成
  - 证据:
    - `python -m pytest tests/...` → 8 passed
    - `src/.../adapter.py` / `SinaAdapter`
  - 尚未证明:
    - 真实外网持续可用性
```

明确区分：

- 已证明；
- 尚未验证；
- 已知不在当前范围。

## 4. 开发中新发现先分类，再决定是否升级

执行阶段的新发现不能自动扩大工作范围。

每条新发现先记录：

```text
发现
证据
影响
分类
```

然后归入：

### A. 当前开发任务内可解决

满足：

- 不改变已批准功能行为；
- 不改变公共接口或长期架构边界；
- 不激活尚未关闭的条件性 blocker；
- 属于当前任务为了满足验收标准必须修复的问题。

处理：

> 记录证据，由执行 Agent 在当前任务范围内处理。

### B. 任务拆解变化

例如：

- 原任务需要拆分；
- 依赖关系发生变化；
- 已有任务被其它任务覆盖；
- 新的执行单元是完成原 Feature 所必需，但不改变功能规格。

处理：

> 返回 `$feature-slice` 更新任务拆解；本 Skill 保留已有执行证据。

### C. 功能定义变化

例如：

- 用户可观察行为需要改变；
- 范围需要扩大 / 缩小；
- 新增数据源 / route / 模式；
- 验收标准需要改变；
- 条件性 blocker 被实际激活；
- 需要新的功能决策 / 风险取舍。

处理：

> 返回 `$feature-shape`。

### D. 项目基线 / 长期架构变化

例如：

- 跨 Feature 公共架构边界改变；
- 长期工程规范需要修改；
- 新增项目级不变量。

处理：

> 返回 Gate A / 项目基线相关流程，并按需记录 ADR。

### E. 独立技术债

不阻塞当前 Feature 时：

> 记录，不顺手处理。

## 5. 人工只处理真正需要判断的例外

以下情况才标记“需要人工判断”：

- 新的产品行为选择；
- 架构边界变化；
- 新的风险取舍；
- 不可逆 / 高风险操作；
- 项目依据之间出现无法由 Agent 客观解决的冲突。

以下情况不要因为“有问题”就自动打断用户：

- 普通 bug；
- 当前任务内缺失测试；
- 可客观核实的实现事实；
- Agent 可以在已批准边界内修复的问题。

原则：

> **升级例外，不升级日常执行。**

## 6. 与 codex-handoff / 其它 handoff 工具的边界

本 Skill **不实现 session handoff**。

它只维护 handoff 工具需要消费的 Feature 级信息：

```text
WHAT
WHY
STATE
EVIDENCE
BOUNDARIES
```

也就是：

- 当前 Feature 目标；
- 已批准决定；
- 当前状态；
- 已完成工作及证据；
- 当前阻塞；
- 剩余工作；
- 不可越过的边界。

`codex-handoff` 或其它 handoff 工具负责：

```text
CONTEXT TRANSFER
SESSION CONTINUITY
```

如果当前环境已经有 handoff 工具，优先复用，不生成另一套重复的续接机制。

## 7. 与成熟执行 Workflow 的关系

本 Skill 不重新实现：

- TDD；
- Debug；
- Worktree；
- Code Review；
- 代码实现；
- Agent 调度。

如果当前 Agent Harness 已提供 Superpowers、Matt Pocock Skills 或其它成熟执行能力：

> 复用它们完成“怎么实现”，本 Skill只维护“为什么做、当前到哪里、证据是什么、何时需要升级”。

如果当前环境无法直接调用某个外部 Skill，不因此复制其完整实现；使用当前 Coding Agent 的原生执行能力，并保持本 Skill 的协作边界。

## 8. 交付收敛检查

当所有当前范围开发任务都被声明完成时，不要直接把 Feature 标成“已完成”。

先检查：

1. 每张完成任务都有与验收标准匹配的证据；
2. 没有未分类的“开发中新发现”；
3. 没有被静默跳过的阻塞项；
4. 没有执行中引入未批准范围变化；
5. 功能规格中的验收标准都有对应证据路径；
6. 当前结果已经具备进入 `$feature-accept` 的条件。

如果满足：

```text
Feature 状态 = 待验收
```

而不是直接宣告最终验收通过。

最终 Feature 是否被接受，由 `$feature-accept` 负责。

## 9. 输出

每次运行结束时更新 `delivery.md`，并向用户输出简洁状态摘要：

```text
功能交付状态

当前阶段:
- ...

已完成:
- ...

当前可继续:
- ...

主要证据:
- ...

当前阻塞:
- 无 / ...

需要人工判断:
- 无 / ...

需要返回上游:
- 无 / $feature-shape / $feature-slice / Gate A

建议下一步:
- ...
```

## 10. MUST / MUST NOT

### MUST

- 保持已批准 Feature 目标和边界；
- 区分功能规格、任务拆解和执行状态；
- 用实际证据支持完成主张；
- 记录开发中新发现并分类；
- 只在真正需要判断时升级人工；
- 在 session / Agent 切换时提供最小 Feature 级续接信息。

### MUST NOT

- 修改已批准 Feature 目标；
- 自主扩大 scope；
- 静默激活条件性 blocker；
- 把 `delivery.md` 变成新的功能规格；
- 自动选择模型或执行后端；
- 调度 Agent / subagent；
- 实现新的 handoff 工具；
- 替代 Coding Agent；
- 创建新的 Workflow Runtime；
- 自动 commit / push。

本 Skill 的目标不是控制 Agent 怎么工作，而是让人和 Agent 在整个 Feature 交付过程中始终共享同一个目标、状态、证据和边界。
