# 项目需求分析与规格说明技能 (Requirements PRD)

这份文档对应软件研发流程中的 **Specify（需求规格化）** 阶段。

它的核心使命是：**把模糊的想法逼成明确的、边界可判断的需求。这份需求说明书必须是一份让项目完全“想透了”、只差翻译成代码的完整规格说明书，任何开发人员或 AI Agent 读完都能无歧义地执行。**

它必须清楚回答：为什么做、给谁用、做什么、不做什么、怎么验收。它回答 What，绝不提前代答 How。

采用项目语言与位置，新项目默认输出 `docs/DemandAnalysis.md`。

---

## 一、 写作核心原则（说程序员人话、想透边界与验收）

1. **回答 What，绝不提前代答 How**：
   - 需求文档只定义“为谁解决什么问题、系统表现出何种可观察行为、验收判定依据是什么”；
   - 严禁在需求中提前规定未讨论的数据库表结构、SQL 锁、框架类库或具体技术选型（这些属于技术方案的职责）。
2. **严禁凭空脑补（消歧提问与显式留白）**：
   - 若用户提供的业务规则或场景不够充分，**严禁 AI 擅自替用户编造业务规则**；
   - 必须主动暂停，向用户提出 2~4 个具体的消歧问题（例如：“当处理失败时，是自动重试还是直接拦截报错？”）；
   - 暂时无法确定的具体阈值或规则，显式标注 `[待用户确认: xxx]`，并在文首《待决事项清单》中汇总统报。
3. **人话叙事，杜绝“条款编号污染”**：
   - 正文采用通俗生动的业务语言叙述场景与规则；
   - 严禁在段落中密集堆砌内部条款编号（如 `[AC-B02-20]` 等）；若引用上游规范，统一收口至文末的《依据索引表》。
4. **必须包含清晰的“不做清单（Anti-Scope）”**：
   - 与“要做清单”同等重要，明确划定本阶段坚决不做的边界，防止开发时范围失控与过度设计。
5. **模块详细需求颗粒度到位**：
   - 按模块逐一写清：模块功能职责、操作接口/命令、数据结构/配置规格、核心业务规则与本模块不做清单，确保下游执行无盲区。
6. **可观察、可判定的验收情境（Observable Acceptance）**：
   - 拒绝模糊描述（如“系统应具备高可用性”）；
   - 场景必须具备经典四要素：**前置状态 (Given) + 触发动作 (When) + 可观察响应 (Then) + 边界异常分支**。
7. **为下游留出端到端垂直切片索引（Vertical Slices）**：
   - 文末按业务闭环梳理最小可验证切片，严禁按“建表、写后端、写前端”等横向碎片切分。

## 二、 工作执行流程

### 阶段一：前置资产读取（硬性门禁）
动笔前必须调用 `read_file` 完整读取以下文件：
1. `references/writing-guide.md` —— 掌握场景化表达、消歧提问、就绪度反问、验收场景设计与垂直切片划分；
2. `references/reference-case.md` —— **研读标杆案例，掌握一份“完全想透了”的工业级需求文档应具备的结构深度与严密颗粒度**；
3. `assets/document-template.md` —— 获取标准需求规格说明书模板骨架。

### 阶段二：开工就绪度反问与人机共创（Readiness & Co-Creation Gate）
一份让任何接手者“无歧义执行”的 PRD，绝非 Agent 凭空默写出来的，必须建立在人类给出的核心边界与业务裁决之上。

#### 1. 高质量需求规格必备的 5 项前提条件（动笔前必须反问自检）：
- **系统本质与核心角色 (Persona)**：系统究竟服务谁？核心操作者是最终用户、运维工程师还是调度系统？（人类提供）
- **核心能力与 3~5 个核心用户故事**：MVP 阶段必须跑通的端到端核心场景是什么？（人类提供/共同梳理）
- **清晰的坚决不做清单 (Anti-Scope)**：首发版本明确排除哪些复杂特性（如多租户、分布式事务、第三方复杂集成）？（人类决策）
- **异常处置与降级哲学**：遇到关键异常或外部故障时，业务期望是“强拦截抛错”、“自动降级静默处理”还是“报警停机人工接管”？（人类决策）
- **业务实体与核心不变量**：哪些核心业务事实必须守恒（如记账必平衡、状态流转不可逆等）？（人类提供/Agent 提炼）

#### 2. 就绪度诊断与交互规则：
- **若输入不足（仅有概括性标题或口头描述）**：
  - **严禁直接假想全套复杂的风控规则与业务逻辑！**
  - Agent 必须在对话中先输出《开工就绪度诊断 (Requirements Readiness)》，明确列出已知背景与缺失的关键业务裁决，并提出 2~4 个精准的业务抉择问题（附带推荐方案供人类裁定）。
- **若输入基本就绪**：
  - 快速与用户确认 MVP 范围与 Anti-Scope，确认无误后再展开各模块详细规格。
- **未决事项显式留白**：
  - 暂时无法确定的具体阈值（如超时时间、重试次数上限），正文使用 `[待用户确认: xxx]`，在文首《待决事项清单》汇总，严禁替用户假定确定值。

### 阶段三：起草需求规格文档
1. 按照 `document-template.md` 填充正文；
2. 完整阐明系统定位、核心能力全景、术语概念、典型场景、模块详细需求、要做与不做清单；
3. 梳理下游候选交付切片索引；
4. 未决事项在文首《待决事项清单》中列出，输出至 `docs/DemandAnalysis.md`。

## 三、 交付检查清单

- [ ] **资产读取门禁**：动笔前是否已实际调用 `read_file` 读取指南、**标杆案例 (`reference-case.md`)** 与模板？
- [ ] **想透度检查**：文档是否包含产品定义、能力全景、典型场景、模块详细需求与验收标准？接手者能否无歧义执行？
- [ ] **消歧与真实性**：输入不足时是否已向用户提问？未决项是否显式标注？有无脑补业务规则？
- [ ] **What 与 How 分界**：是否只讲业务表现与验收，未越界规定技术实现细节？
- [ ] **不做清单完备**：是否明确给出了首版坚决不做的 Anti-Scope 清单？
- [ ] **可判定场景**：核心功能是否有 Given-When-Then 的明确判定情境？
- [ ] **垂直切片索引**：文末是否给出了端到端可验证的切片清单？
