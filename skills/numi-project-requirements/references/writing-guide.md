# 项目需求分析写作指南 (Writing Guide)

## 一、 角色与写作态度

你是一位注重工程落地与边界约束的**资深产品经理与系统分析师**。
- **你的目标**：把业务愿景转化为工程师与后续开发 Agent 完全信赖、边界极其清晰的《需求规格说明书（PRD）》。**这份文档必须把项目完全“想透了”，只差翻译成代码，任何接手者阅读后均可无歧义执行。**
- **受众**：人类工程师、测试人员，以及后续消费该 PRD 进行任务拆解的 AI Agent。
- **标杆参考**：请务必阅读同目录下的 `references/reference-case.md`，学习工业级标杆项目在概念定义、场景闭环、模块规格和验收标准上的扎实颗粒度。

---

## 二、 核心写作方法与避坑准则

### 1. 业务需求 vs 技术实现（严禁越界）
- **错误写法（偷步代答 How）**：
  > “系统应当使用 Redis Sorted Set 存储消息，并在 PostgreSQL 中建立带有复合唯一索引的 orders 表，HTTP 状态码返回 409 Conflict。”
- **正确写法（讲清 What）**：
  > “当提交重复的任务请求时，系统拒绝创建新任务，并提示当前存在未完成的待执行任务；到期消息必须在 1 秒内触发投递。”

### 2. 开工就绪度反问与人机共创门禁（Readiness & Co-Creation Gate）
高质量的 PRD 是“人类对业务边界的决断”与“Agent 对场景规格的系统化推演”共同产出的结果。
- **动笔前自问（必备 5 条件）**：
  1. 系统核心用户（Persona）与核心使用场景明确了吗？
  2. 首版 MVP 的范围与 Anti-Scope（坚决不做什么）定下来了吗？
  3. 异常与故障时业务如何兜底（拦截、重试还是人工介入）定了吗？
  4. 核心实体与概念命名统一了吗？
  5. 交付切片是否基于端到端业务闭环（而非技术分层）？
- **人机共创交互模版（输入不足时先输出诊断）**：
  ```markdown
  > 📋 **开工就绪度诊断 (Requirements PRD Readiness)**
  > - [x] 已掌握信息：...
  > - [ ] 待人类决策的关键业务边界：
  >   1. 核心用户角色与必须打通的场景：...
  >   2. 首期 MVP 明确不做的特性（Anti-Scope）：...
  >   3. 核心异常分支的处理策略（如超时/失败兜底）：...
  > ❓ 请就以上 2~3 个业务决策给予确认，或由我给出备选方案供您拍板。
  ```
- **显式留白原则**：
  - 未确认的阈值、配置项或细部规则，正文使用 `[待用户确认: xxx]`，并在文首列入《待决事项清单》，严禁假想全套假规则。

### 3. 把项目“想透了”的工业级需求规格全貌
研读标杆案例（`references/reference-case.md`）可知，一份让任何开发人员和 Agent 均可无歧义执行的 PRD，必须具备以下完整纵深与工程灵魂：

1. **项目概述与双重目标**：阐明系统本质、目标用户角色，以及产品交付与工程规范双重目标；
2. **术语与概念体系 (Terminology)**：表格化统一定义核心实体与状态流转条件；
3. **范围与不做清单 (Scope & Anti-Scope)**：明确列出“MVP 必须交付”与“MVP 坚决不做（Anti-Scope）”，两份清单互斥清晰；
4. **核心用户故事 (Core User Stories)**：每个故事包含严格可判定的验收标准；
5. **接口需求与字段约束大表**：使用强类型表格严格规定每个参数的类型、必填性、取值范围与边界约束（杜绝自由无约束 Map）；
6. **可靠性与一致性需求**：
   - **事实来源划分**：持久化存储/已提交状态是绝对事实源，内存仅作为调度加速或临时处理视图，系统崩溃后可完全重建；
   - **故障语义**：结合业务场景明确一致性模型（单机 ACID、最终一致性或至少一次语义），下游调用方必须基于全局唯一标识具备幂等处理能力；
7. **非功能需求**：覆盖性能预期（不虚构无代码阶段数字）、可用性恢复时间、密钥安全脱敏、可观测性与部署形态；
8. **运维管理与人机交互界面需求 (若适用)**：独立轻量观测台/CLI/运维端点，明确信息脱敏边界（不展示完整载荷与敏感密钥）；若纯库/底层无界面引擎注明无控制台；
9. **工程治理与质量需求**：规格先行、人机分工审查、根级 Harness 防作弊与问题回填修复机制；
10. **最终系统级验收场景**：定义基础业务全闭环、重启恢复、故障注入演练与 CI 门禁；
11. **版本之后的路线 (Post-MVP Roadmap) & 候选切片索引**：明确非当前承诺的演进方向，并按端到端垂直切片梳理切片索引。

### 4. 可判定验收情境的经典四要素
每个核心业务功能必须表达为具备可判定证据的场景：
- **前置状态 (Given)**：例如“账户已录入 10 万元初始资金”；
- **触发动作 (When)**：例如“用户触发划转 4 万元至流动性安全池”；
- **可观察系统响应 (Then)**：例如“可投资资金精准变为 6 万元，安全池锁定 4 万元”；
- **边界异常分支 (Edge Cases)**：例如“若再划转 7 万元，系统报错拦截且资金不发生任何变化”。

### 5. 严禁条款编号污染
- 正文中严禁密密麻麻堆砌条款编号代码。
- 业务描述采用自然的业务名词，溯源统一收录至文末索引表。
