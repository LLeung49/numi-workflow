# 功能定义

目标：

> **这次究竟要改变什么，怎样才算做对？**

完成后停在 Gate B（功能规格评审）。

## 0. 定位本功能真正需要的资料

先读项目资料索引，只加载当前功能相关的：

- 需求；
- 架构；
- 工程规范；
- 领域术语；
- 适用 ADR；
- 如果本功能依赖当前实现事实，再读取相关现状事实记录。

如果有现状事实记录：

- 优先复用已经验证的结论；
- 只对当前功能需要、且可能已经变化的部分增量核实；
- 不默认重新扫描整个项目。

调研资料 / 参考实现仍然只在真正需要时读取。

外部 review 报告不能作为事实依据，除非已经逐条复核并回写到可信资料。

## 1. 对齐需求和当前代码

读取：

- 当前需求；
- 相关项目依据；
- 相关现状事实；
- 当前功能直接涉及的代码和测试。

代码说明“现在是什么”，项目基线和用户决定说明“应该是什么”。

如果现状事实记录与代码冲突：

1. 核实当前代码；
2. 勘误事实记录；
3. 再继续功能定义。

## 2. 整理功能规格

按顺序：

1. 预期结果；
2. 范围内 / 明确不做；
3. 关键功能行为；
4. 已锁定的架构 / 接口约束；
5. 测试边界；
6. 测试替身隐藏的风险；
7. 验收标准；
8. 待确认事项分类。

测试替身如果隐藏第三方字段、单位、协议、时间语义或数据源行为，补一个最小接口 / 数据约定验证或固定测试样本验证。

## 4. 待确认事项

### 功能定义待确认

不决定就无法确定系统应该如何表现。

### 需调研后确定

必须先通过样本、实验或外部事实才能决定，而且结论可能改变功能行为、公共接口或验收标准。

### 实现细节

功能行为已经确定，开发任务中自行决定即可。

只要前两类中还有会改变行为的事项，任务拆解准备状态就不能标“可开始”。

## 5. Gate B

Gate B 结束时明确：

```text
功能定义状态:
- 已确认 | 待确认 | 部分已确认

任务拆解准备状态:
- 可开始 | 暂不可开始 | 有条件
```

请用户重点看：

- 预期结果和范围；
- 明确不做；
- 公共接口；
- 测试边界；
- 验收标准；
- 功能依据；
- 现状事实引用是否仍可信；
- 待确认事项。

结束时输出：

```text
Gate B 功能规格评审

功能定义状态:
任务拆解准备状态:

预期结果:
范围:
明确不做:

测试边界:
关键验收标准:

规范性项目依据:
相关现状事实:

功能定义待确认:
需调研后确定:
实现细节:
```

不要自动开始任务拆解或实现。
