# 功能定义

目标：回答五个问题：

1. **这次究竟要改变什么，怎样才算做对？**
2. **还有哪些事情没有定下来，它们分别应该由谁解决？**
3. **真正需要用户拍板的事项，基于现有项目原则推荐哪个方案？**
4. **当前真正阻塞任务拆解的事项到底有哪些，哪些只是条件性阻塞？**
5. **其中由 Agent 自己能够核实的当前 blocker，是否已经在合理范围内闭环，而不是原样抛给用户？**

默认先执行事实闭环循环，再停在 Gate B（功能规格评审）。只有用户明确要求“诊断 / 复审模式”或禁止新增调研时，才允许带着仍可由 Agent 继续核实的事实 blocker 停下来展示分类结果。

## 0. 定位本功能真正需要的资料

先读项目资料索引，只加载当前功能相关的：

- 需求；
- 架构；
- 工程规范；
- 领域术语；
- 适用 ADR；
- 如果本功能依赖当前实现事实，再读取相关现状事实记录。

如果有现状事实记录：

- 优先复用已经验证的结论；
- 只对当前功能需要、且可能已经变化的部分增量核实；
- 不默认重新扫描整个项目。

调研资料 / 参考实现仍然只在真正需要时读取。

外部 review 报告不能作为事实依据，除非已经逐条复核并回写到可信资料。

## 1. 对齐需求、当前代码和证据

读取：

- 当前需求；
- 相关项目依据；
- 相关现状事实；
- 当前功能直接涉及的代码和测试。

代码说明“现在是什么”，项目基线和用户决定说明“应该是什么”。

如果现状事实记录与代码冲突：

1. 核实当前代码；
2. 勘误事实记录；
3. 判断是否影响已有需求 / 架构 / 功能规格；
4. 再继续功能定义。

## 2. 客观事实优先由 Agent 核实，不让用户替外部系统拍板

以下问题属于**可客观核实的事实**，默认责任人是 Agent，而不是用户：

- 第三方 API 实际字段和单位；
- 某版本 SDK / 接口的行为；
- 数据源价格口径、日期语义、错误语义；
- 当前代码、配置或数据库实际状态；
- 某个外部协议或格式是否支持某能力。

核实优先级通常为：

1. 与当前使用版本匹配的官方文档 / 协议；
2. 版本化源码或可定位实现；
3. 真实只读响应、固定测试样本或可复现实验；
4. 独立来源交叉验证。

如果来源之间冲突，不要挑一个最方便的结论，也不要让用户决定“事实是什么”；继续做最小必要的定向核实并记录冲突。

如果在合理范围内仍无法证明某事实，则把问题转换成**可确认的功能边界**，例如：

- 该能力暂不支持；
- 该数据源只允许用于对照，不能用于发布；
- 未验证单位的数据只保留原始观测，不进入统一数据格式；
- 无法解释的冲突统一进入人工复核。

此时确认对象是“是否接受这个保守行为 / 范围”，不是让用户猜外部事实。若该保守行为已经由现有需求、ADR 或不变量直接推出且不改变已批准承诺，可以直接据此降为非阻塞；只有它改变功能承诺、覆盖范围或风险边界时才需要新的用户确认。

## 3. 整理功能规格

按顺序：

1. 预期结果；
2. 范围内 / 明确不做；
3. 关键功能行为；
4. 已锁定的架构 / 接口约束；
5. 测试边界；
6. 测试替身隐藏的风险；
7. 验收标准；
8. 未决事项责任归类；
9. 对真正需要人工确认的事项做决策归纳。

测试替身如果隐藏第三方字段、单位、协议、时间语义或数据源行为，补一个最小接口 / 数据约定验证或固定测试样本验证。

## 4. 未决事项先拆问题，再分“问题类型”和“谁负责解决”

每个未决项必须归入以下一类。**一行只描述一种问题性质、一种解决责任和一种阻塞条件。**

| 类型 | 含义 | 默认解决责任 | 是否通常阻塞 Gate B |
|---|---|---|---|
| 外部 / 当前事实待核实 | 世界或当前系统实际上是什么 | Agent 调研 / 代码核实 | 仅当当前已批准范围确实依赖该事实时 |
| 功能决策 | 系统面对某情况应该怎样表现 | Agent 提建议，用户确认 | 是 |
| 架构决策 | 模块边界、公共接口或长期技术方向怎么选 | Agent 提建议；重大/跨功能事项回 Gate A / ADR | 通常是 |
| 风险取舍 | 是否接受安全、兼容、迁移、数据质量等已知风险 | Agent 说明风险并提建议，用户确认 | 通常是 |
| 实现细节 | 不改变外部行为、公共接口或验收标准的局部选择 | 开发 Agent | 否 |

### 必须拆分混合问题

以下任一情况成立就拆成多条，不要揉成一个大 blocker：

- 同一句里同时包含“事实是什么”和“系统怎么办”；
- 两个子问题的解决责任不同；
- 两个子问题的阻塞状态不同；
- 一个子问题可以保守处理，另一个仍必须核实；
- 一个子问题只在某 route / 模式 / 范围被启用时才需要。

例如：

```text
“某备用数据源的价格口径和数据可用时间是否正确？”

拆成：
F-01：价格口径是否满足当前统一数据约定？
→ 当前启用该 route 时属于必要客观事实，可能阻塞

R-01：无法证明 provider 发布时间时，系统用什么时间作为保守可用上界？
→ 若已有点时原则可直接推出安全行为，可不阻塞
```

不要用“证据不足”作为一个模糊的大类。必须继续追问：

> 缺的到底是客观事实，还是一个需要人选择的行为？谁有能力把它解决？当前范围真的依赖它吗？

### 区分当前 blocker、条件性 blocker 和非 blocker

- **当前 blocker**：当前已批准首版范围已经依赖它，未关闭就会迫使开发 Agent 猜。
- **条件性 blocker**：只有启用某 route / 能力 / 范围 / 模式时才会变成 blocker；未激活时不计入当前 blocker 数量。
- **非 blocker**：实现细节、未来优化，或已有批准规则可以安全处理的问题。

条件性 blocker 必须写明**激活条件**。例如：

> 只有首版决定启用 Provider-B 的指数自动补源时，Provider-B 指数 amount 单位才成为当前 blocker。


### 未决事项 ID 只表示问题性质，不表示阻塞状态

新建未决事项统一使用：

- `F-*`：外部 / 当前事实；
- `D-*`：功能决策；
- `A-*`：架构决策；
- `R-*`：风险取舍；
- `I-*`：实现细节。

同一问题家族拆分出的兄弟子项使用 `a / b / c` 后缀，例如 `F-02a / F-02b`。

**不要用 `N-*`、`B-*` 等前缀表达“非 blocker / blocker / 已关闭”。** 阻塞状态属于状态列，不属于稳定 ID。一个 `F-02c` 可以从“条件性 blocker”变成“当前 blocker”再变成“已关闭”，ID 都不变。旧文档中已经存在的历史 ID 不要求为了升级机械改号；仍打开的事项在自然修改时按本规则整理。

## 5. 先判断“这个事实是否真的必须在 Gate B 前知道”

客观事实未知，不等于自动阻塞。先判断当前已批准功能是否真正依赖它。

一项事实只有在同时满足以下条件时才保持为当前 blocker：

1. 当前首版确实会使用相关 route / 能力 / 数据；
2. 如果事实未知，开发 Agent 就无法保证已批准的正确性、接口或验收标准；
3. 不能用已经批准的安全行为隔离它。

以下情况应降为条件性或非阻塞：

- 当前首版不启用该 route；
- 该能力可以明确声明 `unsupported`，且这不违反已批准功能承诺；
- 已批准的 fail-closed / `needs_review` / 不发布 / 保留 raw observation 等规则已经能安全处理；
- 该事实只影响实现优化，不影响行为正确性。

**不要用 `unsupported` 偷偷缩小已经批准的范围。** 如果保守处理会改变已有功能承诺、覆盖范围或风险边界，必须单独形成一个功能决策 / 风险取舍并让用户确认。

反过来，如果保守行为已经由现有需求、ADR 或不变量直接推出，而且不改变已批准承诺，Agent 可以据此把问题标为非阻塞，并说明依据；不需要重复让用户批准同一个原则。

## 6. Research 完成后必须做“决策归纳”

Research 的职责是提供证据，不是自动升级成需求，也不能只留下一句“仍缺证据”。

每轮调研结束后：

1. 把新证据写回调研记录；
2. 把原来的未决项重新分类；
3. 已核实的事实关闭；
4. 仍是客观事实且会阻塞的，由 Agent 继续做**定向**调研；
5. 能通过明确 `unsupported`、缩小首版范围、保守处理等方式消除不确定性的，形成一个功能决策候选；
6. 只把真正需要价值判断 / 产品边界 / 风险接受的事项交给用户。

### 对需要人工确认的事项，Agent 必须先给非绑定建议

不能只把 A / B / C 三个选项丢给用户。

先读取适用的：

- 项目目标和成功标准；
- 已批准需求；
- 架构边界；
- ADR 不变量；
- “明确不做”；
- 当前 Feature 的目标和验收标准。

然后说明：

- 哪个方案最符合这些已批准原则；
- 推荐理由；
- 主要代价 / 风险；
- 为什么其它方案不优先。

**建议不等于批准。** 需要人工确认的事项仍由用户拍板。

只有当现有项目依据确实无法区分方案优劣时，才可以明确写“暂无推荐”，并说明缺少什么判断依据。

### 推荐必须写清触发条件，不能扩大失败语义

推荐方案用“**触发条件 → 系统行为 → 对当前结果的影响**”表达。

不要把：

> “某备用 route 不具备能力”

误写成：

> “整个功能永远不能发布”。

应明确：

> “只有当主路径在某必需日期失败、确实需要该备用 route，且没有其它合格候选时，本批次才因必需数据无法满足而失败；主路径正常时不受影响。”

这是通用规则：**可选能力不可用 ≠ 当前流程必然失败；只有激活了依赖且没有满足已批准契约的替代方案时，才传播失败。**

Agent 推荐默认选择对现有已批准行为**改动最小**、最符合项目不变量和明确不做的方案；如果推荐会新增承诺或扩大范围，必须明确指出。

## 7. 默认执行“事实闭环循环”

`$feature-shape` 的默认行为不是“列出 Agent 还要查什么，然后停下来”，而是：

> **只要当前 blocker 属于 Agent 能在当前授权、范围和合理成本内客观核实的事实，就继续核实、回写、重算，直到它被关闭或出现明确停止条件。**

默认循环：

```text
重新计算当前 blocker
        ↓
选择一个 Agent 负责、当前已激活的事实 blocker
        ↓
做最小必要定向核实
        ↓
把证据写回 research / 现状事实 / spec 的正确层级
        ↓
关闭 / 拆分 / 降为条件性 / 转成需要确认的功能边界
        ↓
重新计算 blocker
        ↓
还有 Agent 可继续闭环的当前事实？
   ├─ 是 → 继续循环
   └─ 否 → 进入 Gate B
```

### 不要把 Agent 自己尚未完成的作业当成 Gate B 待办

如果 `F-*` 仍是当前 blocker，并且 Agent 仍能通过官方文档、版本化源码、当前代码、真实只读响应或小型实验继续核实，就不要仅输出：

> “F-01 仍待 Agent 调研，请用户复审。”

应继续完成最小必要核实。Gate B 面向用户的重点应尽量收敛为真正需要人工确认的 `D-* / A-* / R-*`。

事实项可以继续保留在未决事项表中作为过程记录，但在请求用户确认前，Agent 应尽量把可自主关闭的当前事实项处理完。

### 人工决定可能决定“哪些事实值得查”时，不要穷举所有分支

事实闭环不等于把所有候选 route / provider / 方案都研究完。

如果一个尚未确认的 `D-* / A-* / R-*` 会决定某组事实是否进入当前范围：

1. 先关闭所有与选择无关、且当前主路径必需的事实；
2. 对候选分支只补足**足以形成可靠推荐**的低成本证据；
3. 不为未选中的所有分支做完整契约校准；
4. 用户确认范围后，再激活对应条件性 blocker 并继续事实闭环。

例如：用户尚未决定首版启用哪个 fallback route 时，不应先把五个备用 route 全部做完整校准；应先核实主路径，再对最有现实依据的候选 route 补足推荐所需证据，然后把范围选择交给用户。

### 提交人工决策前先做“决策就绪检查”

`D-* / A-* / R-*` 已经被识别出来，不代表应该立刻打断用户。提交人工确认前必须检查：

> **这个决定现在是否已经有足够事实基础，让用户是在做价值 / 范围 / 风险取舍，而不是替 Agent 补做尚未完成的调查？**

对每个准备提交的人工决策：

1. 列出会直接改变候选方案可行性、推荐方向或风险判断的客观事实；
2. 如果这些事实能在当前授权、当前 Feature 范围和合理成本内做一次低成本、定向核实，先回事实闭环，不提交用户；
3. 只核实**直接影响当前决定**的事实，不因此穷举所有未来 route / provider / 边缘场景；
4. 如果相关事实已经经过有界合理尝试仍因权限、网络、数据、环境或范围限制无法取得，记录为“Agent 闭环受限事项”；此时用户决定的是是否接受由该限制产生的功能边界、风险或研究扩展，而不是事实真假；
5. 用户作出决定后，如果选择激活了新的条件性事实 blocker，立即回事实闭环，不得直接进入 `$feature-slice`。

一个人工决策只有满足以下之一，才算**决策就绪**：

- 直接影响该决定的必要事实已经核实；
- 剩余必要事实已经明确属于 Agent 闭环受限，且当前决定本身正是在选择“接受这个边界 / 风险”还是“授权扩大研究 / 范围”；
- 某些事实只属于未选分支、未来能力或不会改变当前推荐，不需要为了决策完整性继续研究。

如果仍存在一个低成本、直接相关、可由 Agent 自主核实且可能改变推荐的事实，当前 `D/A/R` **尚未决策就绪**，不要提交 Gate B。

例如：若准备让用户决定“是否接受首版指数没有 fallback”，而另一个当前 AkShare 指数 route 尚未做过任何有界验证，就应先核实该 route；只有核实成功，或经过合理尝试确认当前环境无法验证后，这个范围决定才真正就绪。

### 事实闭环的停止条件

只有出现以下情况之一，Agent 才可以带着尚未关闭的事实项停在 Gate B：

- 继续前需要用户先做功能 / 架构 / 风险选择，选择会决定是否还需要该事实；
- 当前环境缺少必要权限、认证、网络、硬件、数据或可访问来源，经过有限的合理尝试仍无法取得；
- 继续核实需要付费 API、写操作、账户交易连接、不可逆操作或其它未获授权的副作用；
- 继续研究会明显扩大当前 Feature，例如引入新的数据源家族、市场或新的产品能力；
- 已经有足够证据支持一个不会污染正确性的保守处理，继续研究不会改变当前行为或验收；
- 用户明确要求“只复审 / 只分类 / 不新增外部调研 / smoke test”。

因为客观限制而无法闭环时，不把事实问题改写成用户可以拍板的事实。标记为：

```text
Agent 闭环受限事项
- 事实问题:
- 已尝试证据:
- 客观限制:
- 当前最安全处理:
- 是否需要用户确认功能边界:
```

### 诊断复审模式是显式例外，不是默认行为

只有用户明确要求“不要新增调研”“只重新分类 blocker”“做 smoke test”等，才进入**诊断复审模式**。

诊断复审模式允许停在：

```text
F-01：仍由 Agent 负责，下一步核实 ...
```

但必须明确写：

> `运行模式：诊断复审；本轮故意不执行事实闭环。`

不能把这种人为暂停误解为正常 `$feature-shape` 已经完成；诊断复审模式下 `任务拆解准备状态` 必须保持“暂不可开始”。

```markdown

## 预期结果

## 范围

- ...
```

## 9. 每次新证据或人工决定后，都重新计算 blocker

不要沿用上一轮“还有 N 个 blocker”的旧结论。以下事件发生后都要重新计算：

- 一个客观事实被核实；
- 用户确认一个功能 / 架构 / 风险决定；
- 首版范围、route 或能力集合发生变化；
- 某个未知被已批准的保守行为隔离；
- 一个混合问题被拆成多个子问题。

重新计算时：

1. 关闭已经解决的项；
2. 重新判断每个条件性 blocker 的激活条件是否成立；
3. 不再使用的 route / 能力对应事实不能继续计入当前 blocker；
4. 如果一个大 blocker 只剩一部分仍需核实，就缩小 blocker，不保留旧的大描述；
5. 更新受影响 REQ / AC、功能规格状态和“当前真正 blocker”列表。

Gate B review 的目标是不断**缩小真正需要解决的问题集合**，而不是机械维持上一轮阻塞状态。

## 10. 什么时候可以停止 Research

Research 的目标不是“把世界研究完”，而是让当前 Feature 的行为不再依赖猜测。

一条客观事实可以在以下任一条件满足后停止继续研究：

1. 已获得足够可信证据，可以写入数据 / 接口约定；
2. 当前首版不再依赖该事实，并已明确移出范围；
3. 已形成安全的保守行为（例如 `unsupported` / `needs_review` / 不进入发布）；如果该行为会改变既有承诺，已经得到需要的确认。

不要为了找到一个万能阈值、覆盖所有特殊日期或证明所有未来版本行为而无限调研。

但也不能把仍然会影响当前发布正确性的单位、字段、价格口径等事实直接留给开发 Agent 猜。

## 11. Gate B（功能规格评审）

Gate B 前先完成默认的事实闭环循环，并重新计算所有**当前激活的阻塞项**。对准备提交用户的每个 `D-* / A-* / R-*` 还必须完成一次**决策就绪检查**。

正常闭环模式下，如果仍存在“Agent 自己可以继续核实”的当前事实 blocker，说明 `$feature-shape` 还没有运行完，不应把它当成 Gate B 待确认项。即使事实不是当前 blocker，只要它低成本、直接影响某个待确认决定且可能改变推荐，也应先核实，再请求人工确认。

Gate B 中的人工决定也可能激活新的条件性事实。用户确认一个 `D-* / A-* / R-*` 后，必须立即重算 blocker；如果对应 `F-*` 被激活，就回到事实闭环循环继续核实，**不能因为“用户已经做完决定”就直接标记为可任务拆解**。

每一项当前 blocker 必须已经满足以下之一：

- **事实已核实**：有足够证据支持；
- **决策已确认**：需要人选择的功能 / 架构 / 风险事项已有明确批准；
- **保守处理已确认**：未知事实不再影响正确性，例如能力不足时明确 `unsupported`；
- **已移出首版范围**：并且范围变化已经得到需要的确认。

“实现细节”不阻塞 Gate B。未激活的条件性 blocker 也不阻塞当前 Gate B，但必须保留激活条件；后续任务如果要启用对应 route / 能力，必须先回 `$feature-shape` 重新评审。

Gate B 结束时明确：

```text
功能定义状态:
- 已确认 | 待确认 | 部分已确认

任务拆解准备状态:
- 可开始 | 暂不可开始
```

只有“任务拆解准备状态 = 可开始”才能进入 `$feature-slice`。

请用户重点确认真正需要人做决定的内容，而不是重新阅读全部研究过程。

正常闭环模式下，Gate B 摘要不应把仍可由 Agent 自主核实的事实列成“请用户处理”的待办。只有因为明确客观限制无法继续闭环时，才单独列“Agent 闭环受限事项”，并说明限制；用户确认的是功能边界 / 风险取舍，不是替外部系统决定事实。

结束时输出一个 30 秒摘要：

```text

- ...
```

如果仍存在 Agent 自己能够核实的阻塞事实，不要把它伪装成“请用户决定”，也不要默认停止 `$feature-shape`；继续执行事实闭环循环。只有命中明确停止条件时才可以停下，并记录“Agent 闭环受限事项”或“诊断复审模式”。
