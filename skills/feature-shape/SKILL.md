# 功能定义

目标：回答三个问题：

1. **这次究竟要改变什么，怎样才算做对？**
2. **还有哪些事情没有定下来，它们分别应该由谁解决？**
3. **真正需要用户拍板的事项，基于现有项目原则推荐哪个方案？**

完成后停在 Gate B（功能规格评审）。

## 0. 定位本功能真正需要的资料

先读项目资料索引，只加载当前功能相关的：

- 需求；
- 架构；
- 工程规范；
- 领域术语；
- 适用 ADR；
- 如果本功能依赖当前实现事实，再读取相关现状事实记录。

如果有现状事实记录：

- 优先复用已经验证的结论；
- 只对当前功能需要、且可能已经变化的部分增量核实；
- 不默认重新扫描整个项目。

调研资料 / 参考实现仍然只在真正需要时读取。

外部 review 报告不能作为事实依据，除非已经逐条复核并回写到可信资料。

## 1. 对齐需求、当前代码和证据

读取：

- 当前需求；
- 相关项目依据；
- 相关现状事实；
- 当前功能直接涉及的代码和测试。

代码说明“现在是什么”，项目基线和用户决定说明“应该是什么”。

如果现状事实记录与代码冲突：

1. 核实当前代码；
2. 勘误事实记录；
3. 判断是否影响已有需求 / 架构 / 功能规格；
4. 再继续功能定义。

## 2. 客观事实优先由 Agent 核实，不让用户替外部系统拍板

以下问题属于**可客观核实的事实**，默认责任人是 Agent，而不是用户：

- 第三方 API 实际字段和单位；
- 某版本 SDK / 接口的行为；
- 数据源价格口径、日期语义、错误语义；
- 当前代码、配置或数据库实际状态；
- 某个外部协议或格式是否支持某能力。

核实优先级通常为：

1. 与当前使用版本匹配的官方文档 / 协议；
2. 版本化源码或可定位实现；
3. 真实只读响应、固定测试样本或可复现实验；
4. 独立来源交叉验证。

如果来源之间冲突，不要挑一个最方便的结论，也不要让用户决定“事实是什么”；继续做最小必要的定向核实并记录冲突。

如果在合理范围内仍无法证明某事实，则把问题转换成**可确认的功能边界**，例如：

- 该能力暂不支持；
- 该数据源只允许用于对照，不能用于发布；
- 未验证单位的数据只保留原始观测，不进入统一数据格式；
- 无法解释的冲突统一进入人工复核。

此时需要用户确认的是“是否接受这个保守行为 / 范围”，不是让用户猜外部事实。

## 3. 整理功能规格

按顺序：

1. 预期结果；
2. 范围内 / 明确不做；
3. 关键功能行为；
4. 已锁定的架构 / 接口约束；
5. 测试边界；
6. 测试替身隐藏的风险；
7. 验收标准；
8. 未决事项责任归类；
9. 对真正需要人工确认的事项做决策归纳。

测试替身如果隐藏第三方字段、单位、协议、时间语义或数据源行为，补一个最小接口 / 数据约定验证或固定测试样本验证。

## 4. 未决事项先分“问题类型”，再分“谁负责解决”

每个未决项必须归入以下一类。一个混合问题如果同时包含事实和决策，必须拆成多条。

| 类型 | 含义 | 默认解决责任 | 是否通常阻塞 Gate B |
|---|---|---|---|
| 外部 / 当前事实待核实 | 世界或当前系统实际上是什么 | Agent 调研 / 代码核实 | 若影响行为、接口或验收则阻塞 |
| 功能决策 | 系统面对某情况应该怎样表现 | Agent 提建议，用户确认 | 是 |
| 架构决策 | 模块边界、公共接口或长期技术方向怎么选 | Agent 提建议；重大/跨功能事项回 Gate A / ADR | 通常是 |
| 风险取舍 | 是否接受安全、兼容、迁移、数据质量等已知风险 | Agent 说明风险并提建议，用户确认 | 通常是 |
| 实现细节 | 不改变外部行为、公共接口或验收标准的局部选择 | 开发 Agent | 否 |

不要用“证据不足”作为一个模糊的大类。必须继续追问：

> 缺的到底是客观事实，还是一个需要人选择的行为？谁有能力把它解决？

## 5. Research 完成后必须做“决策归纳”

Research 的职责是提供证据，不是自动升级成需求，也不能只留下一句“仍缺证据”。

每轮调研结束后：

1. 把新证据写回调研记录；
2. 把原来的未决项重新分类；
3. 已核实的事实关闭；
4. 仍是客观事实且会阻塞的，由 Agent 继续做**定向**调研；
5. 能通过明确 `unsupported`、缩小首版范围、保守处理等方式消除不确定性的，形成一个功能决策候选；
6. 只把真正需要价值判断 / 产品边界 / 风险接受的事项交给用户。

### 对需要人工确认的事项，Agent 必须先给非绑定建议

不能只把 A / B / C 三个选项丢给用户。

先读取适用的：

- 项目目标和成功标准；
- 已批准需求；
- 架构边界；
- ADR 不变量；
- “明确不做”；
- 当前 Feature 的目标和验收标准。

然后说明：

- 哪个方案最符合这些已批准原则；
- 推荐理由；
- 主要代价 / 风险；
- 为什么其它方案不优先。

**建议不等于批准。** 需要人工确认的事项仍由用户拍板。

只有当现有项目依据确实无法区分方案优劣时，才可以明确写“暂无推荐”，并说明缺少什么判断依据。

## 7. 什么时候可以停止 Research

Research 的目标不是“把世界研究完”，而是让当前 Feature 的行为不再依赖猜测。

一条客观事实可以在以下任一条件满足后停止继续研究：

1. 已获得足够可信证据，可以写入数据 / 接口约定；
2. 当前首版不再依赖该事实，并已明确移出范围；
3. 已形成安全的保守行为（例如 `unsupported` / `needs_review` / 不进入发布），且该行为得到需要的确认。

不要为了找到一个万能阈值、覆盖所有特殊日期或证明所有未来版本行为而无限调研。

但也不能把仍然会影响当前发布正确性的单位、字段、价格口径等事实直接留给开发 Agent 猜。

## 8. Gate B（功能规格评审）

Gate B 前先检查所有**阻塞项**。每一项必须已经满足以下之一：

- **事实已核实**：有足够证据支持；
- **决策已确认**：需要人选择的功能 / 架构 / 风险事项已有明确批准；
- **保守处理已确认**：未知事实不再影响正确性，例如能力不足时明确 `unsupported`；
- **已移出首版范围**：并且范围变化已经得到需要的确认。

“实现细节”不阻塞 Gate B。

Gate B 结束时明确：

```text
功能定义状态:
- 已确认 | 待确认 | 部分已确认

任务拆解准备状态:
- 可开始 | 暂不可开始
```

只有“任务拆解准备状态 = 可开始”才能进入 `$feature-slice`。

请用户重点确认真正需要人做决定的内容，而不是重新阅读全部研究过程。

结束时输出一个 30 秒摘要：

```text
Gate B 功能规格评审

功能定义状态:
任务拆解准备状态:

本轮已经核实的关键事实:
- ...

需要用户确认的决策:
- D-01: <问题>
  - 推荐: ...
  - 依据: ...

仍由 Agent 负责继续核实的事实:
- U-01: ...

已采用的保守处理 / 已移出范围:
- ...

不阻塞的实现细节:
- ...

受影响的 REQ / AC:
- ...
```

如果仍存在 Agent 自己能够核实的阻塞事实，不要把它伪装成“请用户决定”；继续做最小必要调研或明确说明无法访问的客观限制。

完成后不要自动开始任务拆解或实现。
