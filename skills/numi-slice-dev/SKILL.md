# 切片交付与串行开发技能 (Slice Development)

本技能负责以单个端到端切片为单位，驱动标准交付流水线。

它的核心使命是：**以模块原料卡为输入，执行开工纪律（核验前序依赖代码物理存在）、驱动 SpecKit 串行开发各阶段（Specify / Clarify / Plan / Tasks）、执行强制软停等（Soft Stop 等待人类确认任务清单与交付物对照）、执行 `/speckit-analyze` 静态交叉一致性预检、严格带门禁调用 `/speckit-implement` 逐任务实施编码（外层适用质量门禁 + 内层专属 Inner Harness）、最终输出 6 证据 DoD 验收与对话级 Review 变更总结。**

输入参数：切片标识（如 `SLICE-01`、`01` 或 `01-account-ledger`）。若用户未指定切片标识，自动读取 `docs/raw-materials/README.md` 全局切片拓扑表，推荐当前前序依赖已就绪且自身尚未交付的最小编号切片。

---

## 一、 总纪律与核心原则（贯穿全程）

> **能机器判的绝不留给人，机器判不了的绝不自行发挥。**

- **硬门禁（机器判，不过不放行，不许绕）**：
  - 分支与工作区物理隔离 100% 合规（一卡一分支、严禁主干直写、严禁跨卡混写、并行强制独立 Worktree）、测试套件全绿、静态代码风格与类型检查 0 报错、交付物白名单存在性 100% 物理核对通过。
- **软门禁（6 项明确触发场景：立即停下、向人类汇报、等确认后继续，不得自行决定）**：
  1. 需要创建原料卡第 11 节交付物白名单之外的任何对外公开概念（public 类型、配置键、数据表/实体、REST 路径、CLI 命令等）；
  2. 需要修改任何已定字面量（类名、方法签名、枚举项、配置键、表列名、端点路径等）；
  3. 原料卡与 `docs/TechnicalSolution.md`（或架构设计基线）发生冲突；
  4. 需要修改前序切片已交付的公共接口（当前原料卡明确列为“改造点/重构点”的除外）；
  5. 第三方 API 在本地依赖环境中核实不到或签名不符；
  6. 需要引入技术方案未列明的第三方外部依赖。
- **反作弊铁律**：
  - 严禁通过删除断言、标记 `@skip`/`@Disabled`、放宽误差公差或修改期望值让测试变绿；
  - “实现错修实现，怀疑测试错停下报告”；
  - 门禁未全绿前绝对不得宣称完成。
- **提交、合并、删除与发布授权**：
  - 全程**严禁自动执行 `git commit`、`git merge`、`git push`、`git branch -d/-D`、`git worktree remove` 或运行部署发布脚本**，代码审查、提交、合入主干及分支/工作区清理时机 100% 由人类决定（AI 仅做只读安全体检盘点）。

## 二、 工作执行流程

### 阶段零：切片输入分流与前置资产读取

#### 1. 切片类型分流 (Slice Type Triage)
解析传入的切片标识，读取目标切片原料卡，识别切片类型并分流处理：
| 切片类型 | 特征与判断依据 | 执行模式 |
| :--- | :--- | :--- |
| **业务实现切片 (Implementation Slice)** | 原料卡包含新增领域实体、服务逻辑、数据清洗与专属单元测试 | **标准模式**：走完整 1~7 阶段（Specify $\rightarrow$ Clarify $\rightarrow$ Plan $\rightarrow$ Tasks $\rightarrow$ Analyze $\rightarrow$ Implement $\rightarrow$ DoD） |
| **串联/集成切片 (Integration Pipeline Slice)** | 原料卡不新增底层业务逻辑，核心是将前序各切片串联成端到端流转流水线或任务管道 | **特殊模式**：不开多余新 feature 类，重点实施跨模块串联调度、落实端到端对账清单，并将对账固化为集成测试 Harness（如 `test_pipeline_integration.py`），验证全链路无断点与数据守恒 |
| **演示/验收切片 (Demo/Showcase Slice)** | 原料卡侧重于最终 CLI 入口、UI 看板展示或策略实盘演练 | **特殊模式**：完成 CLI 入口/交互配置与冒烟对账，重点整理“剩余人工项清单”供用户真实体验，不做重复模块开发 |

#### 2. 前置资产读取（硬性门禁）
动笔前必须调用 `read_file` 完整读取以下文件：
1. `references/writing-guide.md` —— 掌握软硬门禁、SpecKit 装配、强制软停等与 6 证据 DoD；
2. `references/reference-case.md` —— 研读标杆案例，学习工业级切片交付的完整轨迹与 Review 报告；
3. `assets/document-template.md` —— 获取切片验收交付报告模板。

### 阶段一：H0 开工纪律与输入核验
1. **H0-A：上游原料卡就绪度 (DoR) 严格验真与拒收门禁 (Raw Material DoR Audit)**：
   - 检查目标原料卡文件名：**若包含 `*-business.md`、`*-temp.md`、`*-draft.md`，立即拒收 (REJECT)，禁止进入开发！**
   - 检查卡片内容：
     - 若接口方法出现 `run_bXX()`、`process_bXX()` 等泛型伪签名；
     - 若输入单未分层，把系统内部衍生参数（如幂等键、日历推算起始日、对账基准分母）当成用户必填输入混在同一扁平表里；
     - 若出现 `kind`、`expected_keys` 等无业务语义的实现黑话，缺少领域枚举；
     - 若交付物白名单（第 11 节）写“待核验后确定”、“根据实现决定”等推迟空话；
     - 若第 5 节缺乏具体的贯穿业务样本（无具体代码、日期或数值）；
     - 若第 3.1 节缺失《上游架构约束承接表》或遗漏了技术方案中的核心强约束（如旧表旧字段优先、标的覆盖范围）；
     - 若第 7.1 节涉及持久化却缺少三方结构对比，企图以内存对象属性兼容偷换数据库物理表兼容；
     - **只要触碰任一红线，立即停机报错：**
       > `❌【输入原料卡 DoR 审查失败】原料卡 <slice-id> 包含泛型占位符、参数混淆、约束遗漏或以逻辑兼容偷换物理存储，未达到工业级编写深度。已触发拒收保护，拒绝进入代码实施！请先调用 numi-atomic-requirements 对该切片进行单卡深度编制。`
2. **读取 3 样事实源**：
   - 该切片的模块原料卡：`docs/raw-materials/<slice-id>-<meaningful-name>.md`；
   - 对应本切片的技术方案章节：`docs/TechnicalSolution.md`；
   - 前序切片交付物与状态：数据库 migration、已有模块接口契约。
3. **H0-B：前序依赖代码物理存在性核验**：
   - 调用工具或终端命令，实际核查原料卡第 4 节声明的上游依赖类/接口是否在磁盘上存在且非空；
   - 若前序文件缺失或接口不匹配：**立即停机报错，向用户汇报阻断点，严禁强行开工！**
4. **H0-C：独立回查上游架构约束（Anti-Circular Drift Gate）**：
   - **绝不能只相信原料卡自述“无冲突”**；
   - 必须调用 `read_file` 查阅 `docs/TechnicalSolution.md` 对应章节与项目任务书；
   - 独立核对原料卡第 3.1 节《上游架构约束承接表》，确认是否遗漏了核心强约束（如优先旧物理表/旧字段、股票与 ETF 覆盖范围、指定数据源等）；
   - 检查是否存在未经人类明确授权擅自将架构要求“后置”（如将旧表迁移推迟）或“偷换”的行为；
   - **若发现上游强约束被私自遗漏或后置：立即触发硬门禁停机向人类汇报，严禁强行开工！**
5. **H0-D：Git 分支与 Worktree 物理隔离硬门禁（Branch & Worktree Isolation Gate）**：
   - ⚠️ **必须在阶段二 `/speckit-specify` 写入任何 `specs/` 目录或 `.specify/feature.json` 之前完成！绝不依赖可能静默跳过的 Spec-Kit hook 自动建分支！**
   - **第一步：环境探测与只读僵尸巡检（只盘点、绝不擅删）**：
     - 执行 `git rev-parse --git-dir`、`git rev-parse --git-common-dir`、`git branch --show-current`、`git status --porcelain` 与 `git worktree list`，识别主干基线分支 `<base-branch>`（`main` 或 `master`）。本切片专属分支固定命名为 `feat/<slice-id>-<slug>`（直接绑定原料卡编号，严禁使用动态递增序号）；
     - 顺手执行只读分支体检（严禁自动删除任何分支或 Worktree）：扫描是否存在失效 Worktree 路径或历史残留的 `feat/*`、`codex/*` 僵尸分支；若发现已通过 `--no-ff` 第二父节点合入主干的冗余切片分支或长期未合入的疑似废案分支，在 H0 报告末尾附带一行只读盘点提醒供人类决定，**绝不使用粗糙的 `git branch --merged` 无差别批量删除（防止误杀刚创建的 0 提交新分支与长期分支）**。
   - **第二步：识别串行 vs 并行拓扑并强制隔离**：
     - **情形 1：当前已处于独立 Git Worktree 中**（`git-dir != git-common-dir` 且 `git rev-parse --show-superproject-working-tree` 为空）：
       - 核实当前分支正是 `feat/<slice-id>-<slug>` 且无其他切片脏文件，直接放行；若分支串台则立即阻断停机。
     - **情形 2：并行开发多张原料卡**（用户指令要求并行、`git worktree list` 存在其他活跃切片工作区、或主目录处于另一张活跃切片分支且用户开启同层并行卡）：
       - **核查并行准入三前提**：① 公共底座与前置依赖切片已合入 `<base-branch>`；② 本切片第 11 节交付物白名单与并行中的兄弟切片 **100% 零路径重叠**；③ 测试端口与测试库表独立无争用。任一前提不满足，**立即阻断停机报告冲突，严禁强行并行**！
       - 三前提满足时，**绝对严禁与兄弟切片共用同一工作目录切分支**（否则必互相篡改工作区文件并覆盖 `.specify/feature.json`）！优先调用平台原生隔离工作区工具；无原生工具时先确认 `.worktrees/` 已写入 `.gitignore`，再从主干执行 `git worktree add .worktrees/<slice-id> -b feat/<slice-id>-<slug> <base-branch>`（注意：`.env` 等本地配置建议采用指向主仓的软链接，避免在 Worktree 内产生孤本忽略文件），并在该独立 Worktree 目录内执行本切片后续全部阶段。
     - **情形 3：标准单目录串行开发**：
       - 若当前已在 `feat/<slice-id>-<slug>`（本切片断点恢复）：核查未提交改动仅限本切片第 11 节白名单与 `specs/<slice-id>-*` 范围，合规即继续；
       - 若当前停留在**尚未合入主干的上一切片分支**（`git merge-base --is-ancestor HEAD <base-branch>` 返回非 0）或存在其他切片未提交脏文件：**立即触发硬门禁阻断停机**！严禁多张原料卡混在同一分支“一锅炖”，也严禁从旧 `feat/*` 分支直接套娃切新分支；必须提示人类：“检测到上一切片尚未验收合入 `<base-branch>`，请先审查 Commit 并 `git merge --no-ff` 合入主干后再开本切片（若两卡无依赖需并行，请确认开启独立 Worktree）”；
       - 若当前在 `<base-branch>` 或已合入主干的旧分支且工作区干净：**强制先执行 `git switch <base-branch>` 回到最新主干基线**，再执行 `git switch -c feat/<slice-id>-<slug> <base-branch>` 创建并切换到本切片专属分支（严禁直接在 `<base-branch>` 主干编写任何业务或规格文件）。

### 阶段二：组装并执行 `/speckit-specify`
从原料卡装配需求规格，调用 `speckit-specify`。

- **显式绑定切片编号（防撞号与防串台）**：显式指定特性目录 `SPECIFY_FEATURE_DIRECTORY` 为 `specs/<slice-id>-<slug>`（直接对齐原料卡固定编号，如 `specs/b01-prepare-scanner-market-data`，严禁使用易在并行分支间抢号冲突的 `001/002` 自动递增流水号）；Git 分支保持 H0-D 已锁定的 `feat/<slice-id>-<slug>`。
- 参数遵循以下**需求骨架（只写 WHAT / WHY，不带底层类名和内部代码实现细节）**：

> ⚠️ **物理验收契约豁免说明**：所谓“不带底层技术细节”，是指不写业务内部实现代码；**但用户与技术方案明确指定的物理表名、特定外部接口、对外协议和兼容性限制，属于业务验收需求的硬性组成部分（属于 WHAT 而非 HOW），必须在 Specify 的功能需求清单与验收标准中原样保留，严禁作为“实现细节”过滤掉！**

```text
切片【{slice_id}】需求规格：<模块名称> —— <第 1.1 节一句话目标与通俗比喻>

1. 业务背景与价值：
   <第 1.1 节通俗比喻与核心业务价值，为什么需要本模块>

2. 核心用户场景与主路径（Happy Path）：
   <第 5 节具象业务实例与数据流转过程，拆为 2~3 个 Given-When-Then 情境>

3. 外部业务意图入参（仅限【输入单 A】）：
   <第 6.1 节输入单 A：业务意图输入。严禁混入【输入单 B】内部衍生参数>

4. 交付物验收期望（对应【输出单 A】）：
   <第 6.1 节输出单 A：业务可用交付物与下游消费形态>

5. 功能需求清单（Functional Requirements）：
   - FR-01: ...
   - FR-02: ...
   <每条需求必须具备可测试性，对齐第 8 节验收断言>

6. 明确不做（Anti-Scope 边界）：
   <原料卡第 9 节边界与停止条件逐项照搬>

7. 验收标准与关键回归点：
   - 自动化部分由原料卡第 10 节专属 Inner Harness 套件承载（单测全绿即通过）；
   - 关键回归守点：<列出第 10 节写出代码的关键测试用例与第 2.4 节 Top Gotchas 守点>；
   - 剩余人工核验项：<列出涉及外部真实联调或手工走查项>。

8. 上游依赖与假设：
   <第 4 节声明的已物理存在的前序切片接口与外部环境依赖>
```

### 阶段三：执行 `/speckit-clarify`（消歧门禁）
1. 检查原料卡第 5、6、7 节与现有代码基线之间是否存在歧义（如异常码规范、字段公差、特定边界入参行为）；
2. **若存在歧义或上游缺失**：暂停落笔，向用户提出 2~3 个精准消歧问题；
3. 待用户回复确认后再进入下一步；若无歧义，记录“消歧通过，无未决歧义”。

---

### 阶段四：组装并执行 `/speckit-plan`
调用 `speckit-plan`，参数必须由以下**四大工程支柱要素**拼接组装而成：

1. **固定技术栈与配置规范句**：
   `Python 3.11+（或项目基线版本）+ 项目基础框架。动手前核实依赖环境。凭证与敏感密钥走环境变量或配置文件占位，严禁明文硬编码。`
2. **模块分层落位表**（严格对齐项目 DDD 分层与原料卡第 11 节白名单）：
   - 领域模型/枚举/值对象 $\rightarrow$ `src/<domain>/models.py`
   - 参数升格器（Command $\rightarrow$ ExecutionContext） $\rightarrow$ `src/<domain>/service.py`
   - 核心处理流水线 $\rightarrow$ `src/<domain>/pipeline.py`
   - 异常边界与 SkipReason 映射 $\rightarrow$ `src/<domain>/errors.py`
   - 专属 Inner Harness 测试 $\rightarrow$ `tests/unit/test_<domain>.py` 与 Fixtures
3. **测试策略与完成定义句**：
   `测试策略按原料卡第 10 节验收 Harness 执行：实现关键回归单测（覆盖 Top Gotchas 守点），单测默认必跑；集成测试打 marker 区分；实现完成的硬性定义是外层适用门禁 + Inner Harness 专属单测全绿。`
4. **架构红线与 Top Gotchas 防护句**：
   - **三大坑（Top Gotchas）对策转化**：必须将原料卡第 2.4 节指出的三大工程陷阱（如数据量纲缩放、交易日历历史截断、复权锚点漂移、异常零值）转化为具体的代码防御设计（如进入第一站统一规整单位、向前滚动有效交易日并设 `SkipReason` 优雅跳过、显式固定锚点参数），并在 Inner Harness 中编写针对性边界反例测试；
   - 严禁引入原料卡之外的无用公共抽象类；
   - 必须逐条落实原料卡第 2.4 节三大工程陷阱防范逻辑；
   - 接口严禁使用 `kind`、`expected_keys`、`run_bXX` 等偷懒黑话；
   - 避开静态检查解析不了的语法黑魔法。

---

### 阶段五：执行 `/speckit-tasks` 与 🛑 强制软停等（Soft Stop）

1. **调用 `speckit-tasks`**。
2. **Harness 先行（Test-First / Harness Co-Delivery）排期**：
   - 检查任务排序：确认专属 Inner Harness 的 Fixture 与核心测试骨架任务**先于或伴随**对应核心实现任务落地，严禁将所有测试任务堆积在最后。
3. **交付物三态比对与约束覆盖核验（自动核验）**：
   - 任务清单计划生成/修改的文件 $\leftrightarrow$ 原料卡第 11 节交付物白名单；
   - 输出比对结果的三态结论：
     - **齐**：交付物 1:1 闭环覆盖；
     - **缺什么**：遗漏了第 11 节中的哪个文件/测试；
     - **多什么**：超出了第 11 节白名单的新增文件（触碰软门禁，必须剔除或请示）；
   - 检查任务是否触碰了第 9 节不做清单（若触碰立即剔除）；
   - **上游约束覆盖核验**：逐项对照原料卡第 3.1 节《上游架构约束承接表》，确认每个强约束是否有明确的 Task 负责落地与验证。
4. **🛑 强制软停等（Soft Stop）**：
   - 在对话中向人类用户展示三态比对结果、任务清单与上游约束覆盖对照；
   - **若方案拟对上游约束做任何调整、妥协或后置，必须在此处单独红字高亮列出《拟调整架构决定与申请例外》并等待显式批复**；
   - **铁律申明**：人类日常在对话中回复的“继续”、“先让采集器跑起来”仅代表推进执行，**绝对不构成未披露架构变更的授权！** 未经明确披露的架构例外一律无效！
   - 提示人类：“任务清单已生成，已与原料卡交付物及上游架构约束完成三态比对（齐/缺/多），请人类审核确认后回复‘继续’或提出修改建议”；
   - **绝对停下！不得到人类确认，严禁进入后续分析与编码！**

### 阶段六：执行 `/speckit-analyze`（一致性预检）与 `/speckit-implement`（带门禁编码实施）

人类在阶段五的软停点确认“继续”后，正式进入预检与编码实施：

#### 步骤 6.1：执行 `/speckit-analyze`（交叉一致性与纵向穿透预检，强烈建议必跑）
在敲下任何一行业务代码之前，调用 `/speckit-analyze` 对当前切片的 `spec.md`、`plan.md`、`tasks.md`、原料卡与上游技术方案执行全方位静态交叉与纵向溯源比对：
1. **纵向溯源核查（Traceability Check）**：
   - 抽查链路：`TechnicalSolution.md (原始要求) -> 原料卡第 3.1 节承接表 -> spec.md -> plan.md -> tasks.md -> tests`；
   - 严防“下游共谋丢弃”：核查技术方案声明的强约束（如优先旧物理表、股票+ETF覆盖）是否逐级稳定传递，严防下游文档共同遗漏后假装互相一致；
2. **需求覆盖核查（Coverage Check）**：`spec.md` 中的用户故事与 Given-When-Then 断言是否均在 `tasks.md` 中有对应任务？严禁需求悬空；
3. **架构范围核查（Scope Creep Check）**：`tasks.md` 规划的文件与类是否均在 `plan.md` 中有架构支撑？是否严格限定在原料卡第 11 节交付物白名单内，未触碰第 9 节不做清单？
4. **契约签名一致性（Contract Drift Check）**：`tasks.md` 中引用的接口名、枚举名、参数类型是否与原料卡第 6 节及 `plan.md` 契约 100% 吻合；
5. **依赖顺序核查（Dependency Inversion Check）**：测试任务与实体任务是否先于或伴随服务层实现任务，依赖拓扑无循环与倒置。
- **预检判定**：
  - 若分析器检出致命异常（如关键断言漏排、非法蔓延文件、上游强约束掉链），立即就地修订 `tasks.md` 或 `plan.md`，直至分析通过；
  - 确认分析结果通过（0 阻断性异常）后，方可启动编码。

#### 步骤 6.2：调用 `/speckit-implement` 逐任务带门禁编码实施（双执行引擎支持）
人类在阶段五确认“继续”后，正式授权进入连续编码实施阶段。此时支持根据运行环境能力无缝挂接两类执行引擎：

- **引擎 A（强烈推荐：挂接 `superpowers:subagent-driven-development`）**：
  若当前运行环境支持子智能体（如 Codex、Claude Code、Antigravity），**强烈推荐直接唤起 `superpowers:subagent-driven-development` 执行 `tasks.md`**：
  - 主控 Agent 扮演 Orchestrator，将 `tasks.md` 中的每个 Task 派发给全新的 Implementer Subagent；
  - 每个 Task 实施完成后，自动触发 `spec-reviewer`（契约保真审查）与 `code-quality-reviewer`（代码质量审查）独立质询；
  - 主控 Agent 全程不亲自敲业务代码，上下文永远极其清爽，自动连续吞吐推进，物理切断单会话疲劳导致的过早交卷通道。
- **引擎 B（单会话守护：挂接 `superpowers:executing-plans`）**：
  若当前运行环境不支持 Subagent，由当前主 Agent 在单会话中直接执行，严格执行以下纪律与三层门禁守护：

##### 🛑 核心铁律：反过早交卷与连续推进（Continuous Execution & Anti-Premature-Exit）
1. **破除“局部测试通过/无报错 = 任务完成”的幻觉**：
   - 单个 Task 的单元测试通过、Ruff / Lint 格式化通过、或是当前终端无报错，仅仅代表**当前子任务（Task）局部增量成立**，**绝不代表切片开发已结束**；
   - **严禁**一跑通某个局部的单测就自行宣布胜利、停下交卷或向人类“汇报阶段性成果”等待夸奖。
2. **连续任务自动吞吐（Auto-Pipeline）**：
   - 只要 `tasks.md` 中仍有未完成的后续任务（如 T001 完成后还有 T002~T005），必须**自动、连续推进到下一个任务**，保持高速工作流，严禁无故交还控制权。
3. **合法停机/交还控制权的仅有 4 种条件**：
   - 🔴 **[触发软门禁]**：触碰 6 项软门禁之一（遇到未定接口、字面量冲突、需要修改前序切片公共契约、找不到第三方 API 真实签名），必须立即停机向人类请示；
   - 🔴 **[自愈熔断]**：针对同一 Bug 连续修复 3 次失败，或连续 2 次无进展（Zero-diff），立即停机并记录现场至 `docs/session-handoff.md`；
   - 🟡 **[物理资源枯竭预警]**：预判会话单轮步数（Max Steps）或上下文窗口即将耗尽（剩余 < 15%）。此时必须明确声明：“因单轮资源上限暂停，切片**未完成**，已执行任务与剩余待办已落盘至 STATUS.md”，绝不伪称“已完成”；
   - 🟢 **[达成 6 证据 DoD 验收]**：`tasks.md` 全部勾选 100%、外层门禁全绿、Inner Harness 全绿、已落盘 `docs/reports/<slice-id>-acceptance-report.md` 并完成对话级 Review 总结。

##### 三层门禁守护：
1. **写前门禁（H3 依赖验真）**：
   - 涉及第三方库方法（如 Tushare、Pandas、SQLAlchemy 等），先在本地依赖环境中核实方法名与参数签名真实存在；核实不到立即触发软门禁；
   - 涉及前序切片导出的类型或方法，先读源文件验真，核查不到立即停下消歧。
2. **写中门禁（H1/H5 保真与防蔓延）**：
   - **交付物白名单保真**：严格只创建和修改原料卡第 11 节白名单内的文件，绝不自作主张增加未经声明的抽象基类或全局工具类；
   - **不建文档外抽象层**：代码仅限满足当期需求与接口契约，不自行做未经讨论的“过度设计”或“提前泛化”；
   - **已定字面量逐字保真**：类名、方法名、枚举值、数据表列名逐字对齐原料卡与技术方案；
   - **注释只写“为什么”**：代码注释专注文档化“为什么这样设计”（业务动机、边界妥协、Gotchas 防范点），严禁复读代码“在干嘛”；
   - **两层入参严格隔离**：外部接口只接收 `Command`（业务意图），服务层内部做参数升格推导 `ExecutionContext`，严禁让外部调用方感知内部衍生参数；
   - **DDD 统一语言逐字保真**：严禁出现 `kind`、`expected_keys`、`run_bXX` 等无语义黑话，已定枚举名、方法名逐字对齐；
   - **防御 Top Gotchas**：必须原样落实原料卡第 2.4 节设计的三大陷阱防范代码（如防停牌行数不足、防金额千元偏差、防锚点漂移）；
   - **异常与日志守恒**：异常不吞（严禁 bare except / pass），捕获必落日志或映射为领域 `SkipReason`；
   - **测试方法命名规范**：测试方法名必须是语义明确的英文（如 `test_prepare_market_data_skips_when_suspended`），禁止无意义中文方法名；若原料卡给出中文测试用例名，用英文名落地并在 docstring 中保留原文以便对号。
3. **写后门禁（任务级 DoD）**：
   - 原料卡第 10 节验收 Harness 中写出代码的单元测试与断言必须原样落地（断言逻辑逐条保真）；
   - 实现与测试伴随落地，每完成一个任务立即在终端运行该任务对应测试，红了当场修，绝不把问题攒到最后阶段；
   - 自愈预算红线：普通代码 Bug 最多修复 3 次；连续 2 次无进展（Zero-diff）立即停机并记录现场至 `docs/session-handoff.md`。

### 阶段七：6 证据 DoD 验收收尾与 Review 总结
全部任务实施完成后，执行全量验证，逐项获取证据并填入验收报告（`docs/reports/<slice-id>-acceptance-report.md`）：

1. **证据 1：外层适用门禁全绿**：在终端实际运行 `docs/AiProgrammingGuide.md` 规定的当前项目适用且已配置的外层质量门禁（Lint, Test, Build 等），退出码为 0，捕获关键输出。对指南中明确标为未配置/阶段后置的门禁如实说明缺口（标注 NOT_CONFIGURED），不伪造绿灯，亦不作为阻断切片交付的前置条件；
2. **证据 2：Inner Harness 测试全绿**：原料卡第 10 节规定的专属测试全部存在且断言通过，关键回归测试逐个对号；
3. **证据 3：交付物物理核对**：对原料卡第 11 节交付物白名单逐项执行 `ls` / 文件核验，确认物理存在且非空；**若涉及持久化存储，必须核查数据库真实表结构（表名/DDL）或旧 SQL 真实读取测试；严禁用 Python 读取对象的字段存在性冒充数据库物理兼容！**
4. **证据 4：前序切片全量回归绿**：运行前序切片的所有历史测试，确认无任何回归破裂（跨切片契约证据）；
5. **证据 5：全局不变量与架构约束逐条核对**：检查数据守恒、状态外置、涉外 IO 沙箱等底线不变量；**逐条核对原料卡第 3.1 节上游架构约束承接表中的强约束，证明已物理达成且无未经批准的擅自后置**；
6. **证据 6：剩余人工项清单**：列出课件/原料卡中“做完怎么验”的外部真实联调项（真实密钥、实盘通道、页面手工点击等），明确告知用户“Harness 自动化已判卷，这几项等你人工核验”。

**完成声明解耦 (Decouple Completion from Data Coverage)**：
严格区分“架构与功能要求是否完成”与“批量业务数据覆盖度”。允许的数据缺口可标记为“功能通过、数据 PARTIAL”；但若架构物理约束（如旧表兼容、标的资产覆盖）未达成，**切片整体交付状态必须标记为 PARTIAL，严禁因测试通过或跑通了部分数据就宣称完结**！

**变更总结（直接输出在对话中，不另开文件）**：
以 `git status --short` / `git diff --stat` 实测为准，输出三段固定结构：
- **改动点**：按模块分组列新增/修改/删除的文件及动机，触碰前序文件的单独标出；
- **重点 Review 清单**：按风险排序 3~6 条（架构决策、跨切片契约兼容性、静态门禁妥协点），给出文件行级定位；
- **如何验证**：可直接复制执行的终端命令块及预期结果，附剩余人工项；
- **拓扑推进、归并与零丢失清理指引**：
  - 对照 `docs/raw-materials/README.md`，明确指出当前切片状态与拓扑中的下一个候选切片编号，并向人类提供可直接执行的**零数据丢失归并与安全清理命令模板**：
    - **串行单目录模式**：提示人类审查无误后在当前分支 `git commit`，切回主干执行 `git switch <base-branch> && git merge --no-ff feat/<slice-id>-<slug> -m "merge feat/<slice-id>: <摘要>"`，并**在合入后的 `<base-branch>` 上重跑门禁与回归测试确认全绿**；分支指针建议保留至下一张卡顺利推进或当前阶段（Phase）收官后再按阶段清理；
    - **并行 Worktree 模式（严格按 DAG 顺序 + 拆除前防丢三检）**：
      1. 若本分支并非并行组首个合入主干的切片，合入前必须先在自身 Worktree 内执行 `git merge --no-edit <base-branch>` 同步最新主干并重跑全量门禁全绿；
      2. 定位主仓根目录 `MAIN_ROOT=$(git worktree list --porcelain | awk '/^worktree /{print substr($0,10); exit}')`，回到主仓在 `<base-branch>` 执行 `git merge --no-ff feat/<slice-id>-<slug>`，**并在 `<base-branch>` 上跑通全量测试验证合并结果**；
      3. **Worktree 安全拆除前置三检**（注意：`git worktree remove` 即使不加 `--force` 也会静默永久删除 `.gitignore` 忽略的文件！）：① 主干合并后测试已全绿；② `git -C .worktrees/<slice-id> status --porcelain` 严格为空（无漏提交付物）；③ `git -C .worktrees/<slice-id> status --ignored --short` 核查无孤本 `.env*`、`*.db`、`*.sqlite` 或数据缓存文件。三检通过后在主仓执行不带 `--force`、不吞报错的 `git worktree remove .worktrees/<slice-id> && git worktree prune --verbose`；
    - **阶段收官分支安全清理（Dry-Run 预览先行）**：仅对未挂载 Worktree 且顶点确系 `<base-branch>` 某次 `--no-ff` Merge Commit 第二父节点（`^2`）的 `feat/*` 分支执行 `git branch -d`（绝不用粗糙的 `--merged` 防误杀 0 提交新分支；废弃未合入实验分支若需清理，先打 `git tag archive/<branch>` 留底）。

**报告完毕后停止——绝不自动 commit/merge/push/branch -d/worktree remove，所有提交、合并与清理操作 100% 由人类决定。**
