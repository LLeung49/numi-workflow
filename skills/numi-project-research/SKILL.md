# 项目业界调研文档编写技能 (Industry Research)

这份文档是整个软件工程链条的起点。

**调研定位置，需求定目标，方案定路径，指引定执行。先搞清楚这个领域已经有什么、大家怎么解决、痛点在哪。不是为了抄，是为了找到自己的位置和差异化。没有这一步，后面的设计就是拍脑袋。**

采用项目语言与位置，新项目默认输出 `docs/IndustryResearch.md`。

---

## 一、 写作核心原则（说程序员人话、重工程实证）

1. **务实透彻，讲人话，为人而写**：
   - 目标读者是人类工程师和未来的接手者。通俗生动，多用具体的技术和业务故事，拒绝空洞的概念包装。
2. **严禁凭空脑补（消歧提问与显式留白）**：
   - Skill 负责套用框架和理清逻辑，**不能凭空捏造事实**；
   - 若用户给出的输入不足以支撑判断（如缺少关注的竞品、核心痛点模糊），**必须主动向用户提问消歧（提 2~4 个精准问题）**；
   - 若某项事实暂时无法确认，坦诚标注 `[待补充: 具体调研项]`，并在文首列出《待决事项清单》，杜绝虚构竞品内部实现。
3. **拒绝“编号污染”（No Code Spamming）**：
   - 正文一律使用通俗的业务语言与架构术语，严禁在正文大段堆砌条款编号（如 `[AC-B02-20]` 等）；条款溯源集中收口至文末索引表。
4. **归纳主流流派，客观对比**：
   - 不要简单罗列几个 GitHub 仓库的 README，而是提炼出行业 2~4 种主流解法流派，分析各自的底层假设、适用场景与缺陷，给出横向对比表。
5. **客观战略抉择：采用 (Adopt) / 改造 (Adapt) / 自研 (Build)**：
   - 实事求是评估：若已有成熟方案满足 80% 以上需求，应建议**直接采用（Adopt）**；若仅差少量功能，建议**插件扩展（Adapt）**；只有当架构存在不可调和的底层冲突时，才建议**全新自研（Build）**。严禁为了立项强行自研。
6. **提炼底层机理与不做清单（Anti-Scope）**：
   - 调研不仅看产品功能，更要看底层机理（数据模型、状态机、一致性保障），并从竞品的过度设计中提炼出我们**坚决不做什么**。

## 二、 工作执行流程

### 阶段一：前置资产读取（硬性门禁）
动笔前必须调用 `read_file` 完整读取以下文件：
1. `references/writing-guide.md` —— 掌握架构师务实笔调、流派对比、就绪度反问与人机共创方法；
2. `references/reference-case.md` —— **研读标杆案例，学习工业级调研文档在本质分析、流派对比与机理剖析上的深度**；
3. `assets/document-template.md` —— 获取标准文档骨架。

### 阶段二：开工就绪度反问与人机共创（Readiness & Co-Creation Gate）
高质量的调研文档从来不是 Agent 单方面闭门造车“一次性猜出来的”，而是人类的战略判断与 Agent 的技术实证推演**深度共创**的结果。

#### 1. 高质量调研必备的 4 项前提条件（动笔前必须反问自检）：
- **业务痛点与价值假设**：本项目究竟要解决什么问题？现有手工或传统方式最痛的 1~2 个断点是什么？（人类提供）
- **候选对标方案线索**：业界有哪些代表性开源项目或竞品？是指定对标还是由 Agent 在限定领域内检索实证？（人类提供/Agent 检索）
- **底线约束与技术偏好**：有无硬性约束（如轻量级单机优先、特定技术栈、特定许可证、合规隐私要求）？（人类提供）
- **战略选型倾斜**：人类对“直接引入成熟方案 (Adopt)”还是“扩展已有框架 (Adapt)”还是“核心引擎自研 (Build)”有无初步偏好？（人类决策）

#### 2. 就绪度诊断与交互规则：
- **若输入不足（仅有一句模糊想法）**：
  - **严禁直接生成万字文档并自作主张编造竞品！**
  - Agent 必须在对话中先输出《开工就绪度诊断》，明确指出已掌握什么、缺失什么核心判断，并提出 2~4 个精准消歧问题（每题给出推荐选项供人类一键裁决）。
- **若输入基本就绪**：
  - Agent 与人类快速对齐 2~3 个核心选型假设与对比维度，确认无误后再动笔。
- **未决事项显式留白**：
  - 调研中未能实测确认的技术细节（如竞品特定高并发下的实际表现），严禁臆造，必须显式标注 `[待补充/待实测: xxx]` 并在文首列入《待决事项清单》。

### 阶段三：起草调研文档
1. 按照 `document-template.md` 填充正文；
2. 保持语言朴实精炼，段落长度适中；
3. 输出至 `docs/IndustryResearch.md`。

## 三、 交付检查清单

- [ ] **资产读取门禁**：动笔前是否已实际调用 `read_file` 读取指南、**标杆案例 (`reference-case.md`)** 与模板？
- [ ] **消歧与真实性**：输入不足时是否已向用户提问或显式留白？有无凭空捏造竞品参数？
- [ ] **讲人话检查**：正文是否通俗易懂？是否清除了烦人的内部条款编号？
- [ ] **流派与对比**：是否横向对比了主流流派，而非流水账罗列项目？
- [ ] **不做清单落地**：是否明确给出了本项目坚决不做的 Anti-Scope 清单？
