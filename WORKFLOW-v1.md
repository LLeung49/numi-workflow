# Numi Workflow

## 总体流程

numi-workflow 不是固定 SOP，而是一套根据目标、风险和 Agent
能力动态调整的协作框架。

    Idea
     ↓
    Project Discovery
     ↓
    Gate A
     ↓
    Feature Shape
     ↓
    Gate B
     ↓
    Feature Slice
     ↓
    Gate C
     ↓
    Feature Deliver
     ↓
    Feature Accept

------------------------------------------------------------------------

# Phase 1: Project Discovery

目标：

建立项目长期依据。

输出：

-   项目目标
-   架构背景
-   约束
-   领域知识
-   当前状态

核心问题：

> Agent 是否理解项目为什么存在？

------------------------------------------------------------------------

# Phase 2: Feature Shape

目标：

把需求变成可执行 Feature。

重点：

## Fact Closure

客观事实优先由 Agent 核实。

例如：

-   API 行为
-   数据格式
-   技术限制

------------------------------------------------------------------------

## Decision Readiness

用户只需要处理：

-   产品取舍
-   风险授权
-   架构方向

而不是替 Agent 调研。

------------------------------------------------------------------------

# Phase 3: Feature Slice

目标：

生成 Agent 可以独立完成的任务单元。

每个任务：

-   有明确交付
-   有验证方式
-   可 fresh session 接手
-   有停止条件

------------------------------------------------------------------------

# Phase 4: Feature Deliver

目标：

从人工逐 ticket 管理转向目标驱动交付。

未来模式：

    Approved Goal

    ↓

    Task Graph

    ↓

    Agent Execution Loop

    ↓

    Evidence Validation

    ↓

    Graph Update

    ↓

    Continue

只有：

-   新产品决策
-   架构边界变化
-   高风险不可逆操作
-   未解决关键冲突

才升级人工。

------------------------------------------------------------------------

# Phase 5: Feature Accept

目标：

验证 Feature 是否真正完成。

不是只检查：

"代码是否通过测试"

而是检查：

-   是否满足原始目标
-   是否满足验收标准
-   是否保持项目约束
-   是否产生新的风险

------------------------------------------------------------------------

# 自适应协作

numi 不追求固定流程。

协作策略取决于：

    Agent capability
    Harness capability
    Project maturity
    User maturity
    Risk level

例如：

新项目：

    更多澄清
    更多检查
    更小任务

成熟项目：

    目标授权
    Agent 自主执行
    异常升级

------------------------------------------------------------------------

# 用户能力成长

numi 的长期目标不是培养用户写更多 Prompt。

而是培养：

-   定义目标
-   描述边界
-   建立验收
-   管理风险
-   与 Agent 协作

最终从：

    Prompting

成长到：

    Delegation

------------------------------------------------------------------------

# 设计原则

## 复用优先

已有成熟能力：

优先集成。

------------------------------------------------------------------------

## 简单优先

不要为了未来可能性提前复杂化。

------------------------------------------------------------------------

## 证据驱动

自主权随着证据增长。

------------------------------------------------------------------------

## 异常升级

不要让人工管理正常流程。

人工关注：

真正需要判断的问题。
